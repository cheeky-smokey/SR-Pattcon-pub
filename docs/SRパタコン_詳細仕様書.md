## 改訂履歴

- rev.47 の改訂点（アプリと文書のみ。M5キャリコンは rev.46 のまま）: 編み機コントロールの接続先の初期値を ws://192.168.1.50:21075、探索の既定サブネットを 192.168.1 にし、サブネットの候補（SUBNET_PRESETS）を 192.168.0 / 192.168.1 / 10.0.0 / 172.16.0 にした（ほかは直接入力で選べる）。初期値を使うのは最初の起動だけで、つないだ接続先は覚えておき、サブネットは機器の応答から自動で直す。APP_REV を rev.47、APP_DATE を 2026-10-18 にし、4形式を直した。ファイル名の日付は 1017 のまま（1.3・7.2）。

- rev.46 の改訂点（ファームウェアと文書のみ。アプリは rev.45 のまま）: M5キャリコンの選針出力 ONS の論理を、キャリッジの INS と同じ L（GND）= 選針、H（5V）= 平編みに直した。rev.45 までは ONS_ACTIVE_HIGH = true で H を選針として出していて、INS の論理と逆だった。ONS_ACTIVE_HIGH の既定を false にした（true にすると H = 選針になる）。L が選針になったので、起動時は ONS を出力にする前に H（平編み）を出力レジスタに入れておき、出力にした瞬間に L を出さないようにした。電源を入れてから setup() までは M5 が ONS を駆動しないので、インタフェース側で H にプルアップしておく。キャリッジシミュレータ（INS = L で選針）と SRパタコンは変えていない（6.9.1・6.9.7）。

- rev.45 の改訂点（アプリのみ。M5キャリコンは rev.44 のまま）: 編み機コントロールのキャリッジ欄のツールチップに残っていた旧名を、M5キャリコンの記号（rev.44）に直した（カーソル ND1 → IN1、針の数 CCP → INP）。APP_REV を rev.45、APP_DATE を 2026-10-17 にし、4形式を生成し直した。動作は変えていない。あわせて 9.1 のバンドル生成の手順を、実際に使っているもの（esbuild 0.24.0、JSX は既定の React.createElement で変換）に直した（5.5・9.1・9.2）。ファイル名の日付を 1017 にした（SRパタコン多色1017.tsx / .jsx / _cdn.html / _offline.html。1.2）。

- rev.44 の改訂点（ファームウェアと文書のみ。動作は変えていない。アプリは rev.39 のまま）: M5キャリコンの GPIO の記号を、M5 から見た向きで I と O を付け替えた名前にした。ICD（キャリッジの OCD）、INP（ONP）、IPC（OPC）、IN1（ON1）、ONS（INS）。先頭の I は M5 へ入る信号、O は M5 から出る信号。キャリッジとキャリッジシミュレータは従来どおり OCD・ONP・OPC・ON1・INS。KnitCtrl_M5.ino の定数・関数・変数の名前（ONS_ACTIVE_HIGH・IPC_GATE・IN1_GUARD・isrInp・isrIn1・onsOff・ピンの構造体 IoPins など）とシリアルの [IO] 行もそろえ、本書の 6.3.6・6.9・9.2・10・付録A も M5 の記号で書いた（6.9.1）。

- rev.43 の改訂点（ファームウェアと文書のみ。動作は変えていない。アプリは rev.39 のまま）: キャリッジの信号の名前を読みやすく改めた。OCD（キャリッジ方向。旧 HOK）、ONP（編み目カウント。旧 CCP）、OPC（ポイントカム有効区間。旧 KSL）、ON1（カーソル。旧 ND1）、INS（選針。旧 DOB）。先頭の O はキャリッジから出る信号、I はキャリッジへ入る信号。KnitCtrl_M5.ino の定数と関数の名前（INS_ACTIVE_HIGH・OPC_GATE・ON1_GUARD・isrOnp・isrOn1・insOff など）と、シリアルの [IO] 行もそろえた。キャリッジのコネクタ（DIN 7 ピン メス）と XH 8 ピン（ケーブル色）の対応を加えた（ON1 = DIN 1、OCD = DIN 2、INS = DIN 3、ONP = DIN 4、OPC = DIN 5。6.9.1）。rev.42 以前の改訂点は当時の名前のまま。
- rev.42 の改訂点（ファームウェアと音声。アプリは rev.39 のまま）: M5キャリコンの WebSocket の生存確認を、ライブラリのハートビート（全クライアント共通で ping 15 s・pong 待ち 3 s・連続 2 回の失敗で切る＝約 33〜48 秒）から自前の ping に替え、送信相手（SRパタコン）は応答（pong・フレーム）が LINK_TIMEOUT_MS（10 分）途絶えるまで切らないようにした。糸処理などでタブレットがスリープしても 10 分まではつないだままで、編み込みも止めない。探索のプローブなどそれ以外のクライアントは従来並みに PROBE_TIMEOUT_MS（36 秒）で切ってスロットを回収する。10 分で切ったときは音声 24「SRパタコンとの接続が切れました。SRパタコンから接続し直してください。」で警告し（送信中なら続けて音声 12）、相手が BYE なしで閉じたとき（タブレットのブラウザが接続を閉じた等）は、そこから 10 分つなぎ直さなければ音声 24 で警告する。SRパタコンの「切断」（BYE のあとの切断）と本体の A+C 長押しで「SRパタコン接続待ち」の画面になったときは、音声 23「SRパタコンとの接続を解除しました。SRパタコンの接続を待っています。」で知らせる。音声 23・24 を VOICEVOX:青山龍星で足した（7.4・6.9.5・6.9.6）。
- rev.41 の改訂点（ファームウェアのみ。アプリは rev.39、音声は rev.40 のまま）: M5キャリコンの「SRパタコン接続待ち」の画面で、B ボタンで音声の音量を下げ、C ボタンで上げられるようにした（C は短く押して離したとき。長押しは従来どおり WiFi 設定ポータル）。音量は 1〜10 の 10 段階（段階 × 25 を M5.Speaker の音量にする）で、変えるたびにその音量で短く鳴らし、端でそれ以上変えられないときは低い音を鳴らす。セットした音量は NVS（キー vol）に保存し、電源を切っても残す。保存がないときは 8（= 200。それまでの VOICE_VOLUME と同じ）。画面には音量のバーと「n/10」を出し、Core2 は画面の下のボタンの位置に合わせて「A 空通し」「B 音量－」「C 音量＋」を出す。CoreS3 は下のタッチボタンの名前を「B 音量－」「C 音量＋」に切り替える。接続待ちの間は B で開始側を切り替えない（つないだあと、本体の A で空通しを始めたあとは従来どおり）（6.9.5・6.9.6・6.9.7）。
- rev.40 の改訂点（音声とファームの文言のみ。アプリは rev.39 のまま）: 音声ガイドの WAV 22 個を、VOICEVOX の男性の声「青山龍星（ノーマル）」で作り直した（それまでは Open JTalk）。05・19 は「SRパタコン」と読み（「エスアールパタコン」）、空通しは「からどおし」と読む（ユーザー辞書で補う）。M5 の小さいスピーカーでは低音が出ないので 120 Hz 以下を落とし、ピーク −1 dB にそろえた。KnitCtrl_M5.ino は VOICE_TEXT の 05・19 の文を「SRパタコン」にしただけで、処理は変えていない。生成した音声を使うときは「VOICEVOX:青山龍星」とクレジットを記載する（6.9.6）。
- rev.39 の改訂点（アプリのみ。M5キャリコンは rev.38 のまま）: 編み機コントロールのキャリッジ表示で、キャリッジを実際にいる側に置き、矢印をそこから動かす向きへ出すようにした。右へ動かす指示はベッドの左側に置いたキャリッジと右矢印、左へ動かす指示は右側のキャリッジと左矢印になる。動いている間は左右の端へ飛ばさず、動き出した位置から今のトラバースで数えた針の分だけ進め（機器が針位置を合わせられていればその位置）、描く位置をなめらかに移す（useGlide）。以前は動き出した瞬間にキャリッジが行き先の端に描かれ、針位置が分かると途中へ戻るなど、左右へ飛んでいた。空通しの往路で動いたあと止まったときは「左端まで来たら右へ戻す」と戻る向きの矢印を、復路で動いたあと止まったときは「判定中…」を出す（5.5）。

## 1. 概要

### 1.1 目的

### 2.2 データモデル

アプリケーション全体の状態は単一のドキュメントオブジェクト doc に集約される。

```text
doc = {
stitches: number, // 目数（横方向のセル数、1..240）
rows: number, // 段数（縦方向のセル数、1..1000）
palette: string[], // 色コード配列（"#RRGGBB"、常に8スロット固定）
grid: Uint8Array[], // 色番号（0..7）。0 = 地色、p ≧ 1 = 色p
control: number[], // デザイン段ごとの制御4bit（0..15）＝第1パスの制御。多色で a を外した段は bit4（CTRL_A_OFF=16）も立つ
passControl:number[][], // パスごとの制御4bit（第2パス以降。添字0は見ない。無い段は null）
colors: number, // 地色を除く色数 c（1..7）。パス数は passCount(c)
gaugeRatio: number, // 目／段のゲージ比（既定 0.75）
}
```

grid は段（行）優先の2次元配列で、各行は Uint8Array である。grid\[0\] が図案の上端、各行の要素0が左端に対応する。色数の上限が8であるため色番号は0..7に収まり、1目を1バイトで保持できる。パレットは地色（色0）と色1..色7の8スロットで固定され、色数を変えてもスロットは増減しない。色番号はアプリの内部でも書き出しでも詰め直さない（色3だけを使った図案は色3＝第3パスのまま扱い、第1・第2パスは選針のない空のパスになる）。番号を詰めると図案とパスの対応が変わってしまうため、色を減らす操作はすべて「そのマスを地色に戻す」に統一している。各スロットの表示色は任意の24ビット色に変更できる。数値配列に比べて複製が速くメモリも少ないため、最大240目 × 1000段 × 履歴50件でも実用的な大きさに収まる。添字アクセス・slice・subarray・set・reverse・some・for…of はそのまま使えるが、TypedArray の map は数値しか返せないため、文字列へ変換する処理（gridLines）はループで書く。また splice・push・concat のように長さを変えるメソッドは存在しないため、目（列）の挿入・削除は長さの違う Uint8Array を作って set で写す（3.4）。JSON へ書き出すときは通常配列へ戻す。

スウォッチの長押しは、ペン・指・マウスで同じに判定する。押した瞬間にスウォッチがポインタをキャプチャし、押したまま少しぶれてスウォッチの外へ出ても取り消さない。取り消すのは押した位置から 10 ピクセルを超えて動いたときと、マウスがホバーで外れたときだけである。ペン・指でブラウザや OS がジェスチャとして横取りし pointercancel を送ってきた場合も、動いていなければ長押しを続けて 500ms でバーを開く。ペン・指の長押しで OS が右クリック（contextmenu）を出したときは、メニューではなく長押しと同じくカラー変更バーを開き、長押しでバーを開いたあとに離したときの右クリックではメニューを重ねない。マウスの右クリックは従来どおりメニューを出す。スウォッチには touch-action: none と文字選択・長押しメニューの抑止を指定し、ペン・指の長押しをスクロールや文字選択に取られないようにしている。以前はペンで長押しすると、ペン先のぶれやペンのジェスチャで pointerleave が起きて長押しが取り消され、バーが開かなかった（指はブラウザが暗黙にキャプチャするため起きなかった）。

画面に表示する段番号は最下段を「1段目」とする1始まりであり、上へ向かって増加する（最下段 = 段1、最上段 = 段R）。目番号は左端を「1目」とする1始まりであり、右へ向かって増加する（左端 = 目1）。

一方、内部の grid 添字は上端を 0 とする（grid\[0\] = 最上段）。表示上の段N（最下段=1）は内部添字 R−N に対応する。目の内部添字は左端を 0 とし、表示上の N目目は添字 N−1 に対応する。

U-BOX SR バイナリのパターンブロックは、先頭ブロックが最下段（段1）に対応する。parseUBox は各段を読み込んだのち段順を反転して内部表現（grid\[0\] = 最上段）へ整合させるため、バイナリ先頭ブロックが表示の最下段に現れる（実機の段順に一致）。

パターン集のエントリも同じ表現をとる。entry = { s, r, grid, palette, colors, control, passControl } であり、2色か多色かにかかわらず grid（1目 = 色番号）と palette を必ず持つ。colors は地色を除く色数 c で、パス数は passCount(c) で決まる（c = 1 の2色は1パス、c ≧ 2 は c + 1 パスへ展開。4.3.5）。2値の図案行（. と X）はエントリには保持せず、SRテキストの書き出しと1パスの選針データを作るときに gridLines で導出する（色番号0を地色とし、それ以外を X とする）。逆に2値しか持たない入力（SRテキスト、1パスのバイナリ）は linesEntry がグリッドへ起こして取り込む。これにより読み書きの経路で2色と多色を分岐する必要がなくなり、色情報の格納場所は grid と palette の一箇所に限られる。

doc.colors は、図案が使っている最大の色番号を下回らない。別の色数の図案から切り取った範囲の貼り付けや JSON の読み込みで色数の外の色番号が図案に入った場合は、commit() が色数をその番号まで引き上げ、トーストで知らせる（2.3）。書き出しと編み機への転送は使用中の最大色番号でパス数を決めるので、画面の色数と常に一致させておく必要がある。

### 2.3 履歴管理（undo / redo）

doc への変更は原則として commit() 関数を経由する。commit() は変更前のスナップショットを undo スタックへ積み、redo スタックを破棄したうえで新しい doc を確定する。この単一経路化により、1回の編集操作が必ず1件の履歴に対応することを保証している。例外は3つあり、ペンのストローク（開始時に1回だけ履歴を積み、ドラッグ中は doc を直接差し替える）、カラー入力のドラッグ（3.6、setSlotColor の live 指定）、表示設定の gaugeRatio（履歴に積まない）である。

```js
const commit = useCallback((updater) => {
if (busyBlocked()) return; // 転送中は変更を受け付けない
const prev = docRef.current;
pushUndo(prev); // 変更前を履歴へ（上限50件）
let next = typeof updater === "function"
? updater(snapshot(prev)) : updater;
const m = maxColorNo(next.grid); // 図案が使う最大の色番号
if (m > next.colors) next = { ...next, colors: m }; // 色数を引き上げて知らせる
docRef.current = next; // 同期refを先に更新
setDoc(next);
}, [pushUndo, busyBlocked]);
```

snapshot() は palette / grid / control / passControl を配列複製したうえで返す浅い深コピーであり、履歴間での参照共有による破壊を防ぐ。docRef は React の非同期な状態更新を待たずに最新値を参照するための同期ミラーである。

commit() / undo() / redo() の先頭には busyBlocked() による関門を置く。編み機へ転送中はこの関門が真を返して即座に復帰するため、doc は一切変化しない。commit() を通らない経路のうち、ペンのストロークは開始時に、カラー入力は setSlotColor の先頭で同じ関門を通す。これにより描画・変形・貼り付け・全消去・色の変更・各形式の読み込みまでが単一の判定で塞がれる。詳細は 5.4 を参照。

undo / redo の実行時には選択範囲（selection）とゴースト（ghost）を破棄し、目数・段数の入力欄も復元後の値へ同期させる。

## 3. パターン編集機能

### 3.1 モード

画面は「表示モード」と「編集モード」を持つ。既定は表示モードであり、誤操作による図案破壊を防ぐ。目数・段数の変更、プリセット適用、各種描画ツールは編集モードでのみ有効となる。

目数・段数の入力欄の右には「適用」と「新規」を置く。「新規」は入力欄の目数・段数で空の図案を作る。図案に地色以外のマスが残っているときは、消す前に「追加して新規（登録先の番号を表示）」「追加せずに新規」「キャンセル」を尋ねるダイアログを出し、前者ではパターン集へ追加してから消す。パターン集が上限に達している場合は警告だけを出し、図案は消さない。消去は commit() を通すため「元に戻す」で戻せる。

### 3.2 描画ツール

| **ツール** | **識別子** | **動作**                                                                                                                    |
|------------|------------|-----------------------------------------------------------------------------------------------------------------------------|
| ペン       | pen        | ドラッグした軌跡のセルを選択色で塗る。左右対称（ミラー）補助あり。タッチペン・マウスは1タップ、指はダブルタップでマークする |
| 塗りつぶし | fill       | floodFill による同色領域の4近傍塗り替え                                                                                     |
| 直線       | line       | bresenham アルゴリズムによる直線描画。ドラッグ中はプレビュー表示                                                            |
| 矩形       | rect       | 枠線のみ／塗りつぶしを切替可能                                                                                              |
| セル選択   | select     | 矩形範囲の選択。コピー／切り取り／貼り付け／反転／回転の対象となる                                                          |

編集モードのツールバーは、左から 元に戻す／やり直し → セル選択 → ペン → 塗りつぶし → 直線 → 矩形（矩形のときだけ枠/塗りの切替）→ ミラー の順に並べる。「元に戻す」「やり直し」は描画の取り消しに最も使うため、ツールの選択より左に置く。その右に表示倍率（縮小／px／拡大）が続く。表示モードではツールと取り消しの並びは出さない。  
図案のマスを長押し（500ms、LONGPRESS_MS）すると、そのマスを地色（色0）に戻す。セル選択・ペン・直線・矩形のいずれのツールでも同じ操作で、押したまま指が10ピクセル以上動いたときは長押しを取り消して本来の操作（範囲選択・描画・図形）に戻る。指で描くときは1タップ目の長押しでも地色に戻せる（指で描く操作はダブルタップだが、消す操作は誤って柄が増えることがないため1タップ目から受け付ける）。タッチペン・マウスで押したまま、または指のダブルタップで描き始めたあとに押したままにした場合は、その描画と同じ履歴1件に上書きするので、「元に戻す」1回で長押し前の状態に戻る。ミラー中は対称のマスも地色に戻す。すでに地色のマスを長押ししたときは何もせずトーストで知らせる。色番号やパレットのスロットは動かさない（色を減らす操作は必ず「地色に戻す」に統一する。2.2 / 3.6）。塗りつぶしツールは押した時点で領域を塗るため、この長押しの対象にしていない。

ペンツールでマスをマークする操作は、入力の種類（PointerEvent.pointerType）で分ける。タッチペン（pen）とマウス（mouse）は1タップでマークし、指（touch）はダブルタップでマークする（DBLTAP_TYPES = \["touch"\]）。指の1タップ目では描かないので、タブレットで画面に手やそで、ペンを持ち替える指が触れても柄が増えない。タッチペンの先やマウスのクリックは意図した操作だけなので、ダブルタップにしても誤マークは減らない。かえってペン先のわずかなずれで判定が外れ、描けなくなる（rev.16 まではタッチペンもダブルタップで、2タップ目が隣のマスに入ると成立しなかった）。導電ゴムのペン先など、ブラウザが指と区別できないペンは touch になるので、指と同じダブルタップで扱う。DBLTAP_TYPES に "pen" を加えればタッチペンもダブルタップになる。

指のダブルタップは、1タップ目を押してから 500ms（DBLTAP_MS）以内に2タップ目を押し、2タップ目が「1タップ目と同じマス」か「1タップ目の押下位置から 24 ピクセル（DBLTAP_SLOP）以内」のときに成立する。同じマスは必須にしない。マス境界の近くを叩くと、わずかなずれで隣のマスに入るためである。マークは1タップ目のマスに付け、2タップ目がずれた先のマスには付けない。2タップ目が図案の外や制御マス、段番号・目番号の帯へわずかにはみ出したときも、そちらの操作（制御ビットの切替、段・目の選択）にはせず、ダブルタップとして扱う。1タップ目を押している間に指が DBLTAP_SLOP を超えて動いたときは、なぞったとみなしてダブルタップ待ちを取り消す。それ以下のぶれでは取り消さない（長押し待ちは従来どおり10ピクセルで取り消す）。

2タップ目からはそのまま指を動かして続けて描ける（1タップ目のマスを起点に、ドラッグ中のマスを bresenham で補間する）。ダブルタップが成立した時点で直前のタップの記録を捨てるため、3回目のタップで続けてマークされることはない（マーク → 次もダブルタップ、という区切りになる）。ツールを変えたときと編集モードを出入りしたときも記録を捨てる。

指の1タップ目のあと 500ms のあいだ2タップ目が来なければ、何もマークしていないことが分かるよう「指で描くときはダブルタップでマークします」と知らせる。ダブルタップが成立したときと、指を動かしてなぞったときはこの案内を出さない（なぞっただけのときは、描画もマークも行わない）。ペンを選んだときにも、タッチペン・マウスは1タップ、指はダブルタップであることをトーストで示す。

ダブルタップの制限はペンツールを指で使うときだけに掛ける。塗りつぶし・直線・矩形は押した位置を起点とする操作で、触れただけで柄が広がるわけではないため従来どおり1タップで始める。制御4bitのマス目も従来どおり1タップで切り替える。

### 3.3 選択範囲操作

- extractCells(grid, sel) — 選択矩形の内容を切り出して2次元配列として取得する

- stampCells(grid, cells, x, y) — 任意座標へ配列を貼り付ける。グリッド外へはみ出す部分は無視される（切り捨て）。目数・段数を広げて貼るときは、先に広げた図案へ貼る（pasteGhost）

- flipCellsH / flipCellsV — 選択内容の左右／上下反転

- rotCellsCW — 選択内容の時計回り90度回転。幅と高さが入れ替わる

- fillRegion(grid, sel, color) — 選択矩形の単色塗り

貼り付けはゴースト（半透明の仮置き）として表示され、確定操作を行うまで grid には反映されない。移動元がある場合は src として保持し、移動として扱う。

貼り付け・移動・パターン集からのコピー（4.4.7）は、いずれも確定（confirmGhost）で図案へ反映する。ゴーストが目数・段数の外、すなわち右端の右か最上段の上へはみ出しているときは、確定の時点で警告のダイアログを出す。ダイアログには、はみ出したのが目数か段数か、広げたあとの寸法（「目数: 12 → 14（右端に2目追加）」「段数: 10 → 12（最上段の上に2段追加）」）を示し、「広げて貼り付け」「広げずに切り捨て」「キャンセル」を選ばせる。キャンセルではゴーストを残し、位置を直せるようにする。はみ出していなければ、従来どおり確認なしで貼る。

広げるのは最上段の上と右端の右だけである。段は最下段が段1、目は左端が目1なので、この2方向なら既存の段番号・目番号も、段と制御4bitの対応も動かない（寸法の変更 performResize、段・目の追加と同じ考え方。3.4）。広げた段の制御4bitは0、passControl は null とする。左端の左と最下段の下へはみ出した部分は、従来どおり切り捨てる（ダイアログにもその旨を出す）。段・目の追加と貼り付けは pasteGhost の1回の commit で行うので、「元に戻す」1回で貼る前の寸法と図案に戻る。貼った図案に色数の外の色番号が入った場合の色数の引き上げは commit が行う（3.6）。

配置中は、図案の上と右に「配置余白」を足して描く。余白はゴーストの段数・目数ぶん（MAX_R・MAX_S を超えない）で、淡い青の地にマスの目安線を引き、ゴーストのはみ出した部分をそこへ描く。ゴーストは余白の外へは動かせない（fitGhost）。右は余白の端まで、上は余白の段数まで、左と下は少なくとも1目・1段が図案にかかるところまでである。したがって広げた結果が MAX_S・MAX_R を超えることはない。「選択・配置」パレットの見出しの下には、はみ出している量を「はみ出し 目+2・段+2（確定で広げる）」と出す。

上の余白は図案全体をその高さ（ghostOY）だけ下げて描くことになるため、余白が増えたぶんスクロール位置を下げて打ち消し、図案を画面上の同じ位置に保つ。これが打ち消せないと、図案が画面上で下へ動き、ドラッグしている指の下のマスがずれてゴーストが走る。そのため、(1) 配置中はスクロール内容の下に画面1枚ぶんの余白を足し、必ずスクロールで打ち消せるようにする。(2) ゴーストをドラッグしている最中は余白を広げず、指を離した時点で広げる。選択範囲をつかんで移動するときは、つかんだ瞬間にゴーストができるので、最初のドラッグでは図案の中（上端・右端まで）でしか動かせない。指を離すと余白が付き、次のドラッグから外へはみ出して置ける。余白は置いているあいだは縮めない（縮めると同じ理由で図案が動く）。

配置中は、キャンバスのどこを押してもゴーストの移動になる。余白や番号の帯へはみ出したゴーストもつかめるよう、制御マスや番号の帯の操作より先に判定する。ドラッグ中は固定ペインの読み替えをしない（toLocal の raw 指定）。ペインの境目でゴーストが跳ばないようにするためである。指が表示範囲の端（28ピクセル以内）に来たら、その方向へスクロールする。

配置中の Enter は確定だけを行う（keydown で既定の動作を止める）。ボタンを押した直後はそのボタンにフォーカスが残っており、Enter の既定の動作でそのボタンも押されてしまうためである（目→+ を押してから Enter で確定すると1目余分に増える、反転を押してから Enter で確定すると反転がもう一度かかる、などが起きていた）。

選択範囲と貼り付け（ゴースト）の操作は、図案の上に重ねる浮動パレット「選択・配置」に置く。内容は、選択範囲の操作（コピー／カット／ペースト／塗り／削除／左右反転／上下反転／回転／タイル複製／選択解除）と、段・目の追加と削除（段↑+／段↓+／段−、目←+／目→+／目−。3.4）、配置中の操作（左右反転／上下反転／回転／確定／中止）の3段である。使えない操作は disabled にして淡く見せ、見出しに「選択 4×3」「選択なし」「配置中 — ドラッグで移動」「配置なし」と状態を出す（はみ出しているときは、その量も出す）。パレットはツールバーの切り抜きアイコンで表示・非表示を切り替えられ、タイトル帯のドラッグで移動、□ で折りたたみ、× で閉じられる。選択やゴーストが現れた瞬間には自動で開くので、閉じていても必要なときには出てくる（有無が変わった瞬間だけ働くため、選択したまま閉じたパレットが勝手に開き直すことはない）。初期位置は画面の左下（狭い画面では左上）で、パレット窓・全体プレビュー窓と重ならないようにしている。以前は図案の上に差し込む帯だったため、範囲選択を始めた瞬間に帯が現れてスクロール領域ごと図案が下へ動き、ドラッグ中の指の位置と図案のマスが食い違っていた。セル選択とペンの切り替え、表示モードと編集モードの切り替えでも同じずれが起きていた。絶対配置にしたことで、開閉しても折りたたんでも図案の位置は動かない（図案ペインのフロー内の子はスクロール領域だけになる）。

### 3.4 行・列の挿入と削除

グリッド上の右クリックメニューから、対象段の上／下への段挿入、対象目の左／右への目挿入、および段・目の削除が行える。同じメニューは段番号ガター・目番号の帯を長押し（500ms）しても開き、短いタップではその段／目の選択になる（固定ペインの上からでも同じ。3.7）。段の挿入・削除では control と passControl の配列も同じ位置で連動して増減させ、段と制御4bitの対応がずれないようにしている。同じ操作は「選択・配置」パレットからも行える（次段落）。パレットの見出しには、選択範囲があれば「対象:選択範囲」、無ければ「対象:図案の端」と出す。挿入・削除は何本でも1回の commit で処理するので、履歴は1件であり「元に戻す」1回で元の寸法に戻る。

パレットでは、足す側をボタンで選ぶ（addLines）。1行目が段の 段↑+（上に足す）・段↓+（下に足す）・段−、2行目が目の 目←+（左に足す）・目→+（右に足す）・目− である。選択範囲があれば、その上・下・左・右に、選択の段数・目数ぶんを足す（2×3 の選択なら 段↑+ で2段、目←+ で3目）。選択範囲が無ければ、図案の端（最上段の上・最下段の下・左端・右端）に1本足す。以前の「段+」（選択の上、無ければ最上段の上）と「目+」（選択の左、無ければ右端）は、どちら側に足すのかが分かりにくかったので削除した（rev.20 で加えた端専用の ←+・→+・↑+・↓+ も、選択が無いときの動きに含まれるので削除した）。段番号は最下段が段1、目番号は左端が目1なので、足した位置より上の段・右の目は番号が足した本数ずつ大きくなる。トーストでは足した位置と寸法の変化（「選択した段の上に2段追加しました（段数 5 → 7）」など）に加え、番号が動くときはその旨も知らせる。段を足すときは control と passControl も同じ位置に足し（足した段は0と null）、既存の段と制御4bitの対応は変えない。

選択範囲は消さずに図案と一緒にずらす（上・左に足したときは足した本数だけ下・右へ動く）ので、同じ選択のまま続けて押せる。選択が無く配置中のゴーストがあるときは、ゴースト（移動元 src を含む）も図案と一緒にずらすので、ゴーストを置いたまま端を広げ、そのまま確定できる。1回押すごとに1回の commit で、「元に戻す」1回で1回ぶん戻る。足すと MAX_S・MAX_R を超えるときは押せない。転送中も押せない（5.4）。削除（段−・目−）は従来どおりで、選択範囲があればその段・目、無ければ最上段・右端の1本を、確認ダイアログを通して削除する。右クリック／長押しメニューの挿入（上／下に段、左／右に目）も従来どおりである。

目（列）の挿入・削除は、図案の各行が Uint8Array であるため配列長を変える操作が使えない。1目ぶん長さの違う Uint8Array を作り、挿入・削除位置の前後を set で写して間へ地色（0）を置く（挿入）、または詰める（削除）。TypedArray に splice は存在せず、呼ぶと実行時エラーになる（2.2）。削除はパレットからでも右クリック／長押しメニューからでも、必ず確認ダイアログを通す。ダイアログには対象の番号と本数（「段54〜段57（4段）」「目2〜目4（3目）」）、その段・目に描いた図案が失われること、寸法がどう変わるか（「段数: 60 → 56」）、実行後に「元に戻す」で戻せることを示す。キャンセルでは何も変えない。最後の1段・1目は削除できず、その場合は理由を出すだけで削除しない。追加は元に戻せるため確認しない。

### 3.5 プレビューと検証

drawKnitCell() により、単純な矩形ではなく編み目（メリヤス）風のセル描画を行う。基準色の塗りに対し、陰影のV字と光沢のV字を重ねることで編地の質感を再現する。

検証機能では、編み機の制約に起因する2種類の警告を段単位で検出する。

| **検証項目**   | **設定キー**       | **内容**                                                                                    |
|----------------|--------------------|---------------------------------------------------------------------------------------------|
| 段内色数の上限 | colors / maxColors | 1段で使用する色数が上限（既定2色）を超える段を警告する                                      |
| 渡り糸長の上限 | float / floatLimit | 同じ色が次に現れるまでの間隔（＝その糸が裏で渡る目数）が上限（既定5目）を超える段を警告する |

### 3.6 配色パレットと色数

色数は地色を含めた総色数で選ぶ。下限は2色で、これが1パスになる。すべり目・スレッド・レースのように地色1色で編む柄もここに入る。3色以上は色数ぶんのパスになり、最後のパスが地色の柄である（4.3.5）。プルダウンの表示は「2色(レース)／1パス」「3色／3パス」…「8色／8パス」とし、すべり目・スレッドを含む説明はツールチップに置く。

スロットの表示色は任意の24ビット色（#RRGGBB、1677万色）に変更できる。色の編集はパレット窓の下部に開く「カラー変更バー」で行う。バーはスロットの並びの下に現れ、選択中の色番号に対する input\[type=color\] と \#RRGGBB のテキスト入力、および「一括置換…」「全マス地色に」を持つ。既定では閉じてパレットを小さく保ち、スウォッチの長押し（500ms、LONGPRESS_MS）で、その色番号を選んだうえで開く。色数の外の番号は長押しでも選べず、短タップと同じ案内を出す。カラー入力で選んだ色はその場で図案へ反映し、バーは開いたままにする（ドラッグで選び続けられるようにするため）。テキスト入力は「適用」または Enter で確定し、確定できたらバーを閉じる（applyHex）。不正な値のときは色を変えずバーも閉じないので、そのまま直せる。テキスト入力は \#RGB の3桁表記と先頭の \# の省略も受け付け、正規化して大文字の \#RRGGBB として保持する（normHex）。不正な値は適用せず、入力枠を赤くして警告を出す。表示色を変えても色番号と図案は変わらない。

色の指定は必ず画面に出ている入力で行う。画面外に置いた input\[type=color\] へ element.click() を送る方式は使えない。display:none の色入力はブラウザがピッカーを開かないためで、同じく隠している input\[type=file\] が動作するのとは事情が異なる。一方で、操作そのものを長押しだけの裏に置くと「色を変えられない」と受け取られる。そこでパレット窓の見出しに「色」ボタンを常設し、長押しを知らなくてもバーを開けるようにした。バーが開いているあいだはボタンを橙で示し、バーの × と見出しの「色」のどちらでも閉じられる。スロットの下のヒント文にも「スウォッチ長押しでカラー変更バー」と出す。

カラー入力はドラッグのあいだ連続して変更イベントを発火する。これを毎回 commit すると履歴が埋まるため、ひと続きの操作では最初の変更だけ undo を積み、以降は doc を直接差し替える（setSlotColor の live 指定）。したがって色の選び直しは何度行っても undo 1回で元に戻る。スウォッチの右クリック（マウス）で出るメニューの「カラー変更バーを開く」は、長押しと同じ経路（openColorBar）を通る。「この色番号を一括置換」「このマスを地色に戻す」はカラー変更バーの中のボタンからも行える。長押しメニューの「このマスを地色に戻す」は、その色番号のマスだけを地色（0）に戻す。色番号の削除や詰め直しは行わない。番号を詰めると図案とパスの対応が変わってしまうためである。「この色番号を一括置換」は指定した別の色番号へ置き換える。

パレットの各スロットは右下に色番号を小さく添える。編集モードではパターン表示のマスにも同じ見せ方で色番号を描き、どの目がどのパスで編まれるかを図案の上で読めるようにする。色番号 p（p ≧ 1）はそのマスを編むパス番号であり、地色（0）のマスは3色以上なら最終パスで、2色なら非選針として編まれる（4.3.5）。地色（0）のマスにも 0 を入れるが、面積が広く数字が並ぶため、色のついたマスより薄い文字色で置いて図案の読み取りを妨げないようにする。文字色はいずれもマスの明度から選ぶ。1マスが10ピクセル以上のときだけ描き、それより小さいときは数字が潰れて格子が読めなくなるので省く。表示モードでは描かない。

色数を減らすときは、消える色番号ごとに使用マス数を数え、確認ダイアログで「削除する色番号: 色2（37マス）」のように提示したうえで、OK でそのマスを地色に戻す。使用中のマスが無い場合は確認を省いてそのまま適用する。あわせて、使わなくなったパスの制御4ビット（passControl）も切り詰め、制御帯の本数を色数に追従させる。

選択中の色番号（描く色）は常に色数の範囲に収める。色数が下がる経路は色数の変更だけでなく、パターン集からの読込、JSON の読み込み、undo / redo もあるため、doc.colors の変化に追従させ、範囲外になったときは色数の上限の色番号へ戻す。範囲外の色番号を選んだまま描くと、画面の色数は変わらないまま書き出しと転送のパス数だけが増えてしまうためである。

反対に、別の色数の図案から切り取った範囲を貼り付けるなどして色数の外の色番号が図案に入った場合は、commit() が色数をその番号まで引き上げ、「図案に色3が入ったため、色数を4色（4パス）にしました」のように知らせる（2.3）。

メニューの「色の入れ替え」は、パレットと同じ表記（地色／色1／色2…）で、色数の範囲内の色番号だけを並べる。

### 3.7 固定ペイン（段番号・制御マス・目番号）

グリッドを拡大して縦横にスクロールしても、左端の段番号ガター・制御マス4列・指示記号の空け列（幅 M.left）と、上端の目番号・制御ビット凡例（高さ M.top）が見えるように、3枚の固定ペインを重ねる。左ペインは横スクロール時、上ペインは縦スクロール時、左上の角は両方のときに表示する。いずれも本体キャンバスの該当領域を drawImage で転写するため描画処理は二重化されず、見た目・配色・選択ハイライトは本体と一致する。ペインは pointer-events: none とし、当たり判定は toLocal がペイン内の座標へ読み替える。

本体キャンバスはスクロール内容の中で内側余白 PAD の位置に置くのが基本であるが、編集モードでは制御層のドロップリスト（4.2.4）がキャンバスの真上に入るため、その高さぶん（約27ピクセル）下がる。canvasShift は offsetLeft / offsetTop から PAD を引いたずれ量 ex / ey を返し、転写位置と当たり判定の読み替えの両方をこの量で補正する。左ペインはキャンバスの実際の位置（PAD + ey − scrollTop）に合わせて描き、上ペインはラベル帯が PAD より上へ隠れた時点（scrollTop \> ey）から出す。ペイン内の座標は x + ex − scrollLeft、y + ey − scrollTop で求める。

ゴーストの配置余白（3.3）があるときは、キャンバスの上端から ghostOY の位置にラベル帯が来る。toLocal は y から ghostOY を引いた図案の座標を返し、上ペインと左上の角は転写元を ghostOY からにし、表示し始める条件も scrollTop \> ey + ghostOY とする。配置余白が無ければ ghostOY は0で、動作は従来と同じである。

以前は PAD 固定で計算していたため、編集モードで横スクロールすると左ペインが27ピクセル上にずれて描かれ、段8の制御マスを押すと段9が変わった。縦スクロール時も、上ペインのすぐ下の図案を押すと列の選択になっていた。表示モードではずれ量が0であり、動作は以前と同じである。

ドロップリストの行は横スクロールしても左端（PAD）に貼り付き、左ペインの制御マスの真上に残る。左ペインはキャンバス上端より上の部分を塗りつぶさずに透過させ、ドロップリストを隠さない。

## 4. ファイル形式仕様

### 4.1 SRテキスト形式

シルバーリード純正ソフトが扱う可読テキスト形式。1ファイルに複数パターンを収録できる。図案行の並びは最下段（段1）が先頭であり、U-BOX メモリカード形式（4.2、先頭ブロック＝最下段）と同じ向きである。

```text
SR00001 ← パターン見出し（SR + 数字）
24,60 ← 目数,段数
..XX..XX..XX.... ← 図案1段ぶん（. = 地色 / X = 配色）。先頭行が最下段（段1）
..XX..XX..XX....
…（段数ぶん繰り返す）
```

#### 4.1.1 parseSRText(text) の挙動

- 行を走査し、/^SR\d+\$/i にマッチする見出しを検出したら次の非空行を「目数,段数」として解釈する（区切りは半角カンマまたは読点）

- 目数は 1..MAX_S、段数は 1..MAX_R にクランプされる

- 図案行は . と X（小文字 x も許容）のみで構成される行だけを採用する。それ以外の文字を含む行は図案とみなさず読み飛ばすため、見出しと寸法の間に注記が挟まっても段がずれない（採用した行は小文字 x を X へそろえる）

- 行が短い場合は . で右埋めし、長い場合は目数で切り詰める

- 見出しが1件も見つからなかった場合は、. と X のみの行を図案とみなす寛容な解釈へフォールバックする。目数は最長行の長さを採用する

- 図案行は最下段（段1）が先頭のため、読み込んだ段配列を反転して内部表現（grid\[0\] = 最上段）へ整合させる。書き出し（exportSRText）も対で反転し、最下段から書き出す

戻り値は linesEntry で作ったエントリ（{ s, r, grid, palette, colors: 1, control }）の配列である。

### 4.2 U-BOX メモリカード形式（バイナリ）

#### 4.2.1 ファイルヘッダー（7バイト）

| **オフセット** | **サイズ** | **内容**                                                                        |
|----------------|------------|---------------------------------------------------------------------------------|
| 0x00–0x02      | 3          | 識別子。通常 0x53 0x52 0x1F（"SR" + 0x1F）。判定は先頭2バイトの "SR" のみで行う |
| 0x03           | 1          | 変更不可フラグ                                                                  |
| 0x04           | 1          | 予備                                                                            |
| 0x05           | 1          | コピー不可フラグ（0xFF）                                                        |
| 0x06           | 1          | 収録パターン数 − 1                                                              |

#### 4.2.2 パターンブロック（0x07 以降、収録数ぶん連結）

| **相対オフセット** | **サイズ** | **内容**                                                                                                                             |
|--------------------|------------|--------------------------------------------------------------------------------------------------------------------------------------|
| +0                 | 1          | 編み目数 − 1                                                                                                                         |
| +1                 | 1          | 多色編みの色数。上位ニブル＝パス数 P（2色＝0x10 ／ 3色＝0x30 ／ 4色＝0x40。0x00 と 0x20 は現れない）。PC10 の 0x000D と同じ（4.3.4） |
| +2–+3              | 2          | 段数（リトルエンディアン）                                                                                                           |
| +4 以降            | 可変       | 図案データ本体                                                                                                                       |

#### 4.2.3 図案データのビット配置（連続パッキング）

図案データは、1段ぶんのバイト列を通した連番でビットを詰める（連続パッキング）。目 i は byte(i \>\> 3) の bit(i & 7) に格納し、各バイトは LSB(bit0) から MSB(bit7) の順に埋める。1 がマーク、0 が非マークである。ブロック境界（60目）でビット位置を戻さないことが重要で、戻す実装（ブロック単位インデックス）は60目を超えた時点で4目ぶんのずれを生じる。この連続パッキングは、60目を超える U-BOX SR バイナリが実機で正しく表示されることを確認済みである（2026年9月、確定）。

1段のデータ長は 8バイト × ブロック数 である。ブロック数は ceil(目数 ÷ 60) で求め、最大4ブロック（＝240目）である。目数が60を超えるぶんは byte7 の上位ニブルから次バイトへ連続して格納される。

```text
blocksPerRow = clamp(ceil(stitches / 60), 1, 4)
rowBytes = blocksPerRow * 8
// 目 i の格納位置（行のバイト列を通した連番＝連続パッキング）
byte = rowBase + (i >> 3)
bit = i & 7 // 各バイト LSB(bit0) → MSB(bit7)
mark = (b[byte] >> bit) & 1 // 1 = マークする(X) / 0 = しない(.)
```

目の並びは左端が先頭である。左端の目（目1）が各段データの先頭ビット（byte0.bit0）に格納され、右へ向かって bit1, bit2 … と進む。すなわちバイナリを先頭から読むと左端の目から順に現れる。

#### 4.2.4 制御4ビット

制御4ビットは、その段の行末バイト（byte rowBytes−1）の上位ニブルに格納される。連続パッキングでは図案ビットがこの位置に達しないため、図案と競合しない。

機器バイナリでの制御ビット割当は bit0=ブザー／bit1=下送り（段+）／bit2=上送り（段−）／bit3=予約 である（実機確認済み）。この並びはアプリ内部表現（bit3=ブザー…）と逆順のため、読み書きの境界でビット反転（nib4rev）して整合させる。詳細は付録B を参照。

多色パターンでは段がパスに分かれるため、制御4ビットもパスごとに存在する。デザイン段の制御4ビット（doc.control）は色番号1のパス、すなわち第1パスの制御4ビットとする。指示記号のビットも落とさずそのまま採り、編集画面には機器が第1パスへ出す指示がそのまま見える。第2パス以降の制御4ビットは doc.passControl に段ごとの配列として保持し、書き戻しでも失わない。passControl\[段\]\[0\] には読み込み時に第1パスの値も入るが、参照しない。第1パスの値を control と二重に持って OR すると、編集で control だけが変わったときに古いビットが残り、ブザーを消しても表示と転送からは消えずファイルからは消える、という食い違いが起きるためである。編集画面の制御マスの描き方は、モードで変わる。編集モードでは、ドロップリストで選んだ色パス（2色は色1パス）のビットだけをマスいっぱいに描く。非編集モードでは、マスをパス数ぶんの横帯に分割し、全パスの制御ビットを並べて描く（上端の帯が第1パス）。マークの色はそのパスの表示色で、2色パターンは1パスしかないので既定では黒一色になる。ブザーだけは色ではなく機器の動作なので、どのパスでも橙（BUZZ_COLOR）で塗る。地に埋もれる淡い色（輝度0.88超）のときだけ暗色へ落とし、帯には細い縁取りを入れる。指示記号は、編集モードでは選んだ色パスの記号を、非編集モードでは記号を持つ最も小さいパス番号の制御ビットに従って描き、色はいずれもそのパスの色とする。表示・書き出し（entryPasses）・編み機への転送はいずれも passControlOf が返す同じ値を用いる。第1パスは control\[段\] の下位4bitに、多色では指示記号 \<（制御4）を重ねた値（編集画面の表示に限り、CTRL_A_OFF の印がある段は a を下ろした値）、第2パス以降は passControl の値（無ければそのパスの指示記号）である。

制御ビットの表示と編集の対象は、編集モードで制御マスの真上に置くドロップリストで選ぶ（ctrlSel）。ドロップリストは縦横どちらへスクロールしても制御マスの真上に残す（sticky）。2色（1パス）は色1パスしか無いので、ドロップリストは「色1(レース・すべり目)」を示したまま無効にし、制御マスはそのまま色1パスのブザー・指示ビットを編集する。多色（n色 = nパス）の選択肢は「色1パス(パス1)」〜「色(n−1)パス(パスn−1)」である。最終の色nパスは地色（色0）を編むパスで、地色と同じ図案になるため選択肢に出さず、編集もしない（読み込んだファイルが持つ値は保持し、非編集モードの表示・書き出し・転送には従来どおり使う）。既定は色1パスで、選んだ色パスのブザーと制御ビットだけを表示し、制御マスを押すとそのパスのビットが切り替わる。色数を減らして選んでいたパスが無くなったときは、選べる最大の色パスへ寄せる。以前は既定が「制御ビット表示モード」（多色では表示専用で、押しても変わらない）で、選択肢に地色のパスも並んでいた。

色1パスの層はデザイン段の制御4ビット（doc.control）そのものを、色2パス以降の層はそのパス固有の制御4ビット（doc.passControl\[段\]\[パス−1\]）を表示・編集する。色2パス以降は、未設定の段では指示記号を初期値として編集を始めるので、記号を消さずにブザーだけを足せる。多色の色1パスの aビット（指示記号 \<）も押して付け外しできる（次段落）。ドロップリストの各項目は対応する色を背景に敷き、文字色は背景の輝度で白か黒を選ぶ（色1は黒地に白文字）。制御マスは、セル選択を含むどのツールでも編集できる。以前はセル選択ツール（編集モードに入ったときの初期ツール）では誤操作防止のため無効にしていたが、編集モードに入ってすぐ制御マスを押してもマークできず、不具合と受け取られたためやめた。

多色の色1パスの aビット（指示記号 \<、制御4）は、機器が第1パスに期待する値である。編集画面では段ごとに付け外しでき、外したときはその段の control に印 CTRL_A_OFF（bit4 = 16）を立てて bit2 も下ろす。もう一度押すと印を消して bit2 を上げる。この印は編集画面の表示だけに効く。passControlOf は表示用の呼び出し（asShown）のときだけ、印のある段の a を重ねずに返す。編み機への転送（ctrlRows）と U-BOX・PC10 への書き出し（entryPasses）は asShown を付けずに呼ぶので、印に関係なく多色の色1パスには必ず a を付けて出す。印の無い段は表示でも a を出すので、この印を知らない版で作った図案やファイルも結果は変わらない。2色（1パス）では印を見ず、下位4bitをそのまま制御として使う（2色の a はふつうのビットとして付け外しでき、そのまま出る）。

現在のパターンの JSON とパターン集ファイルには、control の値を印ごと（0〜31）保存し、読み込みでもそのまま戻す（パターン集ファイルの検査は control だけ 0〜31 を正とする）。したがって画面で外した表示は保存しても残る。U-BOX・PC10 のファイルには印は書かれず、色1パスは常に a ありで書かれるので、それらを読み込み直した段は a ありの表示になる。U-BOX・PC10 の読み込み（designControls）は印を付けず、ファイルの色1パスの値をそのまま取り込む（rev.23 では a の無い段に印を付けていたが、出力が常に a ありになったためやめた）。以前（rev.22 まで）は a を固定値として扱い、第1パスの層ではこのマスに斜線を重ねて押しても変えなかった。

ドロップリストはキャンバスの真上に置くため、編集モードではキャンバスがその高さぶん下がる。固定ペインはこのずれを補正して描画と当たり判定を行う（3.7）。

```js
// 4bitニブルのビット順反転（bit0↔bit3, bit1↔bit2）
const nib4rev = (n) =>
(((n & 1) << 3) | ((n & 2) << 1) | ((n & 4) >> 1) | ((n & 8) >> 3)) & 0x0F;
// 制御 = 行末バイトの上位ニブル
control[row] = nib4rev((b[rowBase + rowBytes - 1] >> 4) & 0x0F);
```

#### 4.2.5 parseUBox(buffer) の戻り値

```text
{
magic: boolean, // 先頭が "SR" であればtrue（形式判定）
entries: [entry], // binToEntry の戻り値（2.2 の entry ＋ truncated / passFallback）
truncated: boolean, // データが途中で終了していればtrue
}
```

次パターンへの移動は、クランプ前の実データ長（rows × rowBytes）で進める。クランプ後の値で進めると、上限を超えるパターンが含まれるファイルで以降の読み取り位置がずれる。

段順について、バイナリは最下段（段1）を先頭ブロックとして格納する。parseUBox は読み込んだ段配列を反転して返すため、内部表現では grid\[0\] が最上段（バイナリ末尾ブロック）、最終添字が最下段（バイナリ先頭ブロック）となる。

各パターンは binToEntry でエントリにする。色数フィールドのパス数 P で段列を検証し（isNPassExpanded：段数が P の倍数で、各デザイン段のどの目も高々1パスでしか選針されない）、成り立てば色番号グリッドへ畳み込む。P が2以上なのに成り立たない場合は2色（1パス）として読み、元のパス数を passFallback に残す。読み込み側（importUBox / importPC10）はこれを見て「色数ヘッダが3パスでしたが、パス展開として成り立たないため2色(1パス)で読み込みました」と知らせ、黙って2色へ落とさない。PC10（parsePC10）も同じ扱いである。

#### 4.2.6 U-BOXカードの書き出し（buildUBox）

パターン集の全パターンを1枚のカード像として書き出す。buildUBox(entries) が parseUBox の対をなし、読み込みと同一の規約でバイト列を組み立てる。書き出しファイル名は U-BOX.bin である。

ヘッダー7バイトのうち 0x00–0x02 は識別子 0x53 0x52 0x1F、0x06 は収録パターン数 − 1 を格納する。0x03 変更不可フラグ・0x04 予備・0x05 コピー不可フラグには、実カードで観測される通常値（0x00 / 0x00 / 0xFF）をそのまま書き出す。これら3バイトの意味は未確定であり、実機での確認が必要である（10章参照）。

各パターンブロックは 0x00 に 編み目数 − 1、0x01 に多色編みの色数（上位ニブル＝パス数 P。2色 0x10 ／ 3色 0x30 ／ 4色 0x40）、0x02–0x03 に段数（リトルエンディアン）を置き、以降へ段数ぶんの図案データを連結する。1段あたりのバイト数は ceil(目数 / 60) を1以上4以下に丸めた値の8倍である。

段の並び順と制御4ビットの扱いは parseUBox と対称である。内部表現は grid\[0\] が最上段のため、書き出し時に段配列を反転して最下段（段1）を先頭ブロックとする。制御4ビットは nib4rev で反転してから行末バイトの上位ニブルへ格納する。段数に満たない図案行は地色で右埋めし、制御が未設定のパターンは全段 0 として書き出す。

段配列と制御配列は、段数ぶんの長さに揃えてから反転する。長さの異なる配列を先に反転すると段と制御の対応がずれるためである。

```js
const pl = entryPasses(e); // 多色は P パス段へ展開（制御4ビットは passControlOf）
const lines = Array.from({ length: r }, (_, y) =>
(pl.lines[y] || "").padEnd(s, ".")).reverse();
const ctrl = Array.from({ length: r }, (_, y) =>
((pl.control || [])[y] || 0) & 0xf).reverse();
```

往復整合は目数 1 / 8 / 24 / 59 / 60 / 61 / 64 / 119 / 120 / 121 / 180 / 240 について確認済みである。ブロック境界となる60目と61目、および上限の240目を含め、図案・制御・寸法が1ビットも変化しない。

U-BOXカード1枚に収録できるのは256件までである（UBOX_MAX。0x06 が「収録パターン数 − 1」の1バイトのため）。パターン集が256件を超える場合、exportUBox は確認ダイアログで件数と書き出す範囲（SR00000〜SR00255）を示し、OK で先頭256件だけを書き出す。キャンセルでは書き出さない。トーストには実際に書き出した件数を出す。以前は buildUBox が黙って256件に切り詰め、トーストにはパターン集の総件数を出していた。

### 4.3 PC10（パタコン）形式 .DAT

1ファイル＝1パターンのバイナリ形式。buildPC10(entry, patternNo) が生成する。

| **オフセット** | **サイズ** | **内容**                                                                                                                                                                                                       |
|----------------|------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 0x0000–0x0001  | 2          | 識別子 "SR"（0x53 0x52）                                                                                                                                                                                       |
| 0x0002–0x0006  | 5          | パターン番号（ASCII 5桁、ゼロ埋め）                                                                                                                                                                            |
| 0x0007–0x000A  | 4          | 拡張子文字列 ".DAT"                                                                                                                                                                                            |
| 0x000B         | 1          | セパレータ 0x00                                                                                                                                                                                                |
| 0x000C         | 1          | 編み目数 − 1（U-BOX 形式と同一。4.3.1 参照）                                                                                                                                                                   |
| 0x000D         | 1          | 多色編みの色数。上位ニブル＝1デザイン段あたりのパス数 P（2色＝0x10 ／ 3色＝0x30 ／ 4色＝0x40。0x00 と 0x20 は現れない）。U-BOX のパターンブロック +1 と同じ意味。実機確認済み（2026年9月）。4.3.4 / 4.3.5 参照 |
| 0x000E–0x000F  | 2          | 段数（リトルエンディアン）                                                                                                                                                                                     |

#### 4.3.1 0x000C の解釈に関する注記

受領した仕様書では 0x000C は「編み目数」そのものと記載されているが、実際には U-BOX 形式で同じ意味を持つ量と同一の「編み目数 − 1」である。この点は実機により確認済みである（2026年9月）。

したがって本実装は (目数 − 1) を格納する。素の目数を格納すると全パターンで1目ぶんのずれを生じるため、この箇所を変更してはならない。

実機由来の SR00000.DAT でもこの解釈が成り立つ。0x000C = 0x1C は目数29を表し、純正パターンブック No.100 の「42段29目」という表記と一致する（4.3.5 参照）。

```text
header[0x0c] = clamp(s - 1, 0, 255); // 編み目数-1（実機確認済み。U-BOXと同一）
```

#### 4.3.2 ビット並びの相違（U-BOX との差）

PC10 の図案データは、連続パッキング（目 i = byte(i\>\>3) の bit、行末バイト上位ニブルが制御）である点は U-BOX と同一である。相違は各バイト内のビットの並び順のみで、U-BOX が LSB(bit0)→MSB(bit7) であるのに対し、PC10 は MSB(bit7)→LSB(bit0) と逆順である（実機確認済み）。

したがって、各段データの先頭ビットは byte0 の bit7 となる。左端の目（目1）は byte0.bit7 に入り、右へ向かって bit6, bit5 … と進む。制御4ビットは行末バイト（1ブロックなら byte7、2〜4ブロックでは byte15 / byte23 / byte31）の下位ニブル（bit3–bit0）に位置し、U-BOX（上位ニブル）とは逆側になる。

| **項目**                  | **U-BOX**                                | **PC10**                                 |
|---------------------------|------------------------------------------|------------------------------------------|
| バイト内ビット順          | LSB(bit0) → MSB(bit7)                    | MSB(bit7) → LSB(bit0)                    |
| 目1（左端）の位置         | byte0.bit0                               | byte0.bit7                               |
| 制御4ビットの位置         | 行末バイト（byte7/15/23/31）の上位ニブル | 行末バイト（byte7/15/23/31）の下位ニブル |
| 図案パッキング / 制御位置 | 連続 / 行末バイト上位ニブル              | 同左（同一）                             |

実装上は、まず U-BOX と同一の並び（連続パッキングによる配置＋制御ニブルの nib4rev）で各バイトを組み立て、最後に各バイトを bitrev8（ビット並び反転）して PC10 バイナリとする。

段の並び順は、最下段（段1）を先頭ブロックとして書き出す。内部 grid は grid\[0\] = 最上段のため、buildPC10 は最下段（最終添字）から順にブロックを生成する。これにより U-BOX 読み込み（先頭ブロック = 最下段）と往復整合し、U-BOX を読み込んで PC10 に書き出すとブロック順・図案・制御が保存される。

```js
// 1バイトのビット並びを反転（PC10 は各バイト MSB→LSB）
const bitrev8 = (b) => {
b = ((b & 0xF0) >> 4) | ((b & 0x0F) << 4);
b = ((b & 0xCC) >> 2) | ((b & 0x33) << 2);
return (((b & 0xAA) >> 1) | ((b & 0x55) << 1)) & 0xFF;
};
// U-BOX相当に組んだ後、各バイトを反転
for (let k = 0; k < rowBytes; k++) rowBuf[k] = bitrev8(rowBuf[k]);
```

#### 4.3.3 PC10形式の書き出し経路

PC10 は1ファイル＝1パターンの形式である。ファイル名はパターン名（SR + 5桁）に拡張子を付した SR00000.DAT 形式であり、ヘッダー 0x0002–0x0006 に格納するパターン番号と常に一致する。本体に加えて索引ファイル SRDS.IDX（4.3.6）が必要である。

書き出しはいずれも ZIP 1本で行う（4.3.7）。対象の違いで3経路を用意する。

| **経路**        | **対象**                | **ZIPの内容**                                    |
|-----------------|-------------------------|--------------------------------------------------|
| 全てのパターン  | パターン集の全件        | SRDS.IDX（N=件数）と Dnnn/SRxxxxx.DAT を件数ぶん |
| 現在のパターン  | 編集中のパターン1件のみ | SRDS.IDX（N=1）と D000/SR00000.DAT の2ファイル   |
| パターン集の1件 | 一覧で選んだ1件のみ     | SRDS.IDX（N=1）と D000/SR00000.DAT の2ファイル   |

現在のパターンを書き出す経路はパターン集の内容に影響されない。全件の経路でパターン集が空の場合は編集中のパターン1件を対象とするため、その状況では両者の結果は一致する。パターン集の1件を書き出す経路は、一覧およびパターン選択窓の DAT ボタンから起動する（編集モードでは DAT ボタンは無効。4.4.7）。

ファイルを1つずつ発行する方式は用いない。複数ファイルの連続ダウンロードはブラウザ側の許可設定に依存し、許可されていない場合は1件目だけが保存されて以降が失われるためである。ZIP ならダウンロードは1回で済み、この制約を受けない。

```js
const zipSRDS = (files) => { … }; // 配置してZIP化(4.3.7)
const exportPC10Zip = () => zipSRDS(srdsFiles()); // 全件
const exportPC10Single = (entry) => zipSRDS([ // 1パターン(共通)
[buildSRDSIdx(1), "SRDS.IDX"],
[buildPC10(entry, 0), `${srName(0)}.DAT`],
]);
const exportPC10Current = () => exportPC10Single(現在のパターン);
// パターン集のDATボタン: exportPC10Single(選んだエントリ)
```

1パターンを書き出す2経路は exportPC10Single() を共用する。パターン集の何番目を選んだ場合でも、パターン番号は 00000 に振り直す。ZIP内のファイル名も .DAT ヘッダー 0x0002–0x0006 のパターン番号も 00000 となり、単独のカードとして成立する形にそろえる。

#### 4.3.4 実ファイルによる検証（SR00000.DAT）

実機由来の PC10 ファイル1件（SR00000.DAT、352バイト）を全バイト解析し、本節の解釈と矛盾がないことを確認した（2026年9月）。ヘッダーの実測値は次のとおりである。

```text
53 52 30 30 30 30 30 2E 44 41 54 00 1C 30 2A 00
"SR" "0 0 0 0 0" ". D A T" 0x00 | 0x1C | 0x30 | 0x002A
```

0x000C = 0x1C は「編み目数 − 1」であるから 29目、0x000E–0x000F = 0x002A は 42段を表す。目数29に対する1段あたりのバイト数は ceil(29 ÷ 60) = 1ブロック ＝ 8バイトであり、42 × 8 = 336 バイトとなる。これはファイル長 352 からヘッダー16バイトを引いた値と一致する。目数・段数・ファイル長の三者が整合するため、0x000C を「編み目数 − 1」と解する 4.3.1 の判断は、この実ファイルによっても裏付けられた。

ビット並びについては、各バイトを MSB→LSB の順に読むと左右対称の整った図案となり、LSB→MSB で読むと崩れる。4.3.2 のビット順もこの実ファイルで確認できた。

行末バイト（byte7）の下位ニブル、すなわち内部表現での制御4ビットは 4 / 2 / 6 の3段周期であった。付録B の指示記号では \< ／ ＊ ／ { に対応する。ブザービット（内部表現 bit3）は全42段で 0 である。

一方 0x000D は、当初「セパレータ 0x10」と解釈していたが、実測値は 0x30 であった。これはセパレータではなく、上位ニブルが1デザイン段あたりのパス数 P を表す（本ファイルでは 3）。n色編みは n パスであるから、3色のとき 0x30、4色のとき 0x40 となる。例外は2色で、非選針がそのまま地色になるため地色ぶんのパスが要らず 1パス、すなわち 0x10 である。したがって 0x20（2パス）が現れることはない。0x00（地色のみ）は平編みであって柄そのものが不要であるから、該当するパターンは存在しない。すなわち値は必ず 0x10 以上になる。U-BOX 形式のパターンブロック +1 も同じ意味を持つ。実機確認済み（2026年9月）。buildPC10 / buildUBox はこの値を書き出し、parsePC10 / parseUBox はこの値からパス数を読む。

#### 4.3.5 多色パターンの格納（Pパス展開）

PC10 は1目1ビットの形式であるため、3色以上のパターンはビット面を増やすのではなく、1デザイン段を色数ぶんの段へ展開して格納する。編み機は1デザイン段につき色数ぶんのキャリッジ走行を行い、各走行でその色に属する目だけを選針する。n色編みは n パスであり、最後のパスは地色（色番号0）の柄になる。地色のパスは他のどのパスにも選ばれなかった目の集まりであるから、その柄は自動的に決まり、ユーザーが描くものではない。2色だけは例外で、非選針がそのまま地色になるため地色ぶんのパスが要らず、1パスで足りる。したがってパス数は 1 → 3 → 4 → 5 … と飛び、2パスの多色は存在しない。

パス数の下限は1である。地色のみ（0x00）は平編みであり柄そのものが不要であるから、パターンとして存在しない。書き出しでも 0x00 は作らず、色数フィールドは必ず 0x10 以上になる。一方、すべり目・スレッド・レース編みは糸としては地色1色で編むが、選針データすなわち柄を持つ。これらは2色編み（1パス）として扱う。したがってアプリが扱う色数は地色を含めて2色以上であり、doc.colors（地色を除く色数）の下限は1となる。

実ファイル SR00000.DAT は 42段 ＝ 14デザイン段 × 3パス であった。連続する3段について、次の2点を全14組で確認している。

```text
完全被覆 : 3段の論理和が 目1〜29 の全ビットで 1
排他 : 3段のうち任意の2段の論理積が 0
```

すなわち各目はいずれか1つのパスでのみ選針される。最終パスが地色ぶんであるため、排他でありさえすれば被覆は自動的に成り立つ。これは多色ジャカードの選針データが満たすべき必要条件であり、このファイルが3色パターンであることの根拠となる。指示記号が 4 / 2 / 6（\< / ＊ / {）の周期で並ぶことも、3段で1デザイン段を構成することと符合する。

パスと色の対応は、パス p（p \< P）が色番号 p、最終パス P が色番号0（地色）である。本ファイルでは第1パスが色1、第2パスが色2、第3パスが地色となる。指示記号はパス位置で固定され、第1パスが \<（制御4）、第2パスが ＊（制御2）、第3パスが {（制御6）に対応する。パターンブックの3枚のチャートを各パスの選針データとそれぞれ突き合わせて確認した。

段数フィールド（0x000E–0x000F）はデザイン段数ではなく展開後の段数を格納する点に注意する。デザイン段数は 段数 ÷ P で求める。

29目目（最右端）は図案データであり、第3パスにのみ立つ。第3パスは地色ぶんであるから、この1目は全14デザイン段で地色（色番号0）で編まれることを表す。純正パターンブック No.100「多色ジャカード編（3色）42段29目」の3枚のチャートと全ビットが一致することを確認した（2026年9月）。

したがって図案の幅は29目である。0x000C は 29 − 1 ＝ 0x1C であり、4.3.1 の「編み目数 − 1」と整合する。29目すべてが図案であるから、読み込み・書き出しのいずれでも最終目を特別扱いする必要はない。

各デザイン段で3パスが選針する目数の合計は、全14段でちょうど29であった。余剰ビット領域（目30〜60）に立つビットはない。制御4ビットも 4 / 2 / 6 が全42段で欠けなく3段周期をなす。

色数フィールドの下限は 0x10 で、0x00 は書き出さない。読み込みで色数フィールドと選針データが合わない（展開として成り立たない）場合は2色として読み、その旨を知らせる（4.2.5）。

```js
// 読み込み: P段 → 1デザイン段（d = 下から数えたデザイン段 / c = パス番号−1）
for (let d = 0; d < rows / P; d++)
for (let c = 0; c < P - 1; c++) // 最終パス(地色)は読み飛ばす
for (let i = 0; i < s; i++)
if (bit(d * P + c, i)) grid[rows / P - 1 - d][i] = c + 1;
```

ブロックは最下段（段1）から並ぶため、d は下から数えたデザイン段である。内部表現は grid\[0\] が最上段なので、書き込み先を 段数 ÷ P − 1 − d へ反転させる。この反転を省くと図案が上下逆に復元される。書き出しはこの逆の対応で、最下段のデザイン段から順に P 段へ展開する。

なお、この展開規則は PC10 に固有のものではなく、U-BOX 形式でも同様に成立すると考えられるが、多色の U-BOX 実ファイルは未入手であり未確認である。

#### 4.3.6 SRDS 索引ファイル（SRDS.IDX）

SRDS システムは、パターン本体を SRxxxxx.DAT として個別に保持し、その収録数と各ファイルの存在状態を索引ファイル SRDS.IDX に持つ。実ファイルの比較から、先頭に固定ヘッダがあり、続いて64ビット単位の存在ビットマップが並ぶことが判明している。バイト順は領域によって異なる。ヘッダの4バイト値（0x08 / 0x0C / 0x10 / 0x14）はビッグエンディアンで、存在ビットマップの64ビットワードだけがリトルエンディアンである。ファイル長は 2072 バイトの固定長であり、収録数によって変化しない。内訳はヘッダ24バイトとビットマップ2048バイト（256ワード）で、ビットマップの容量は 16384 件にあたる。

| **オフセット** | **長さ** | **内容**                                                                |
|----------------|----------|-------------------------------------------------------------------------|
| 0x00           | 8        | 識別子 "SRDS.IDX"                                                       |
| 0x08           | 4        | 0x00000010（ビッグエンディアン）                                        |
| 0x0C           | 4        | 0x00000000。フィールドの意味は未確定。10章参照                          |
| 0x10           | 4        | データ数 N（ビッグエンディアン）                                        |
| 0x14           | 4        | データ数 N（0x10 と同値。ビッグエンディアン）                           |
| 0x18–0x817     | 2048     | データ存在ビットマップ。64ビット単位、256ワード固定。リトルエンディアン |

ビットマップは収録されているデータの位置に対応するビットを立てる。先頭から N ビットぶんを立て、使用するワード数は ceil(N / 64) である。N が64の倍数でない場合、最後に使うワードは下位 N%64 ビットのみが1となる。それ以降、ビットマップ領域の終端 0x817 までは 0x00 で埋める。

N=3 の場合、データ数はビッグエンディアンのため 0x10 から 00 00 00 03 と並ぶ。一方ビットマップはリトルエンディアンのため、先頭ワードは 07 00 00 00 00 00 00 00 となる。通し番号0のビットはワードの先頭バイトの最下位ビットに位置する。同じファイル内で向きが逆になるため、読み書きのいずれでも取り違えに注意する。

PC10 .DAT および U-BOX の段数フィールドはリトルエンディアンである（4.2.2 / 4.3）。実機由来の SR00000.DAT で段数42が 2A 00 と格納されていることから確定している。したがってビッグエンディアンなのは SRDS.IDX のヘッダ4バイト値だけであり、それ以外の多バイト値は本仕様書の全体を通してリトルエンディアンである。

```js
const buf = new Uint8Array(2072); // 未使用領域は0のまま
const words = Math.ceil(N / 64); // 先頭ワードから順に埋める(LEで格納)
// N=3 → bitmap[0] = 0x0000000000000007 → 07 00 00 00 00 00 00 00 (LE)
// N=64 → bitmap[0] = 0xFFFFFFFFFFFFFFFF → FF が8バイト
// N=65 → bitmap[0] = 0xFFFFFFFFFFFFFFFF, bitmap[1] = 0x0000000000000001
```

0x0C は実機由来のファイルでも 0x00000000 であり、この値で PC10 側が読み込めることを確認済みである。したがって書き出す値は確定しており、buildSRDSIdx は 0 を書き出す。このフィールドが何を表すのかは未確定であるが、値の食い違いはないため実害はない。値は定数 SRDS_FIELD0C として切り出してある。

N が0のときもファイル長は2072バイトで、ビットマップ全体が 0x00 となる。書き出し経路では対象が1件以上あるため、この状態は通常発生しない。N が容量の16384を超える場合は16384に丸める。

#### 4.3.7 SRDS一式のZIP書き出し

索引と全パターンを1つのZIPにまとめて書き出す。ダウンロードが1回で済むため、ブラウザの連続ダウンロード抑止を受けない。ファイル名は SRDS.zip に固定する（SRDS_ZIP_NAME）。以前は書き出した日付を付けた SRDSyyyymmdd.zip としていたが、日付ごとに別名のZIPが増えて、どれをカードへ入れたのか分からなくなり混乱のもとになったため固定にした。同じ名前のファイルがすでにダウンロード先にあるときは、ブラウザが「SRDS (1).zip」などの別名を付ける（上書きはしない）。ZIP の中の名前は SRDS.IDX と Dnnn/SRxxxxx.DAT のままで、カードへ展開する内容は変わらない。

##### 4.3.7.1 ZIPの構成

圧縮は行わず、格納方式は stored（圧縮方式 0）のみを用いる。外部ライブラリに依存せず、ローカルファイルヘッダ・中央ディレクトリ・終端レコードを自前で組み立てる。CRC32 は標準多項式 0xEDB88320 による。ファイル名はASCIIのみを想定している。

索引 SRDS.IDX はZIP直下に置く。パターン本体は100件ごとのディレクトリ Dnnn へ振り分ける。

配置とZIP化は zipSRDS() に集約しており、全件の経路と現在のパターン1件の経路が同じ処理を通る。したがって収録件数によらずカード上の構造は常に同じである。書き出しファイル名はいずれも SRDS.zip である。

```text
SRDS.zip
├─ SRDS.IDX
├─ D000/ SR00000.DAT 〜 SR00099.DAT
├─ D001/ SR00100.DAT 〜 SR00199.DAT
└─ D002/ SR00200.DAT 〜 …
```

##### 4.3.7.2 ディレクトリの振り分け規則

nnn は通し番号を100で割った整数部であり、3桁ゼロ埋めで表記する。通し番号は0始まりで、SRxxxxx の xxxxx と一致する。1件目から数える場合は (件数 − 1) ÷ 100 の整数部と同じ値になる。

```js
const srdsDir = (i) => "D" + String(Math.floor(i / 100)).padStart(3, "0");
```

| **何件目** | **SR番号**         | **ディレクトリ** | **備考**                          |
|------------|--------------------|------------------|-----------------------------------|
| 1 〜 100   | SR00000 〜 SR00099 | D000             | 最初の100件                       |
| 101 〜 200 | SR00100 〜 SR00199 | D001             |                                   |
| 201 〜 300 | SR00200 〜 SR00299 | D002             |                                   |
| 16384      | SR16383            | D163             | SRDS.IDX のビットマップ容量の上限 |

1つのディレクトリに入るのは常に100件である。ディレクトリのエントリはZIPに明示的には含めず、パスに含まれる階層から展開側が生成する。

### 4.4 パターン集の管理

読み込んだパターンと編集中のパターンは、パターン集（library）として1つの配列に保持される。パターン集はフローティングのパターン選択窓とメニュー内の一覧の双方から操作でき、各形式への書き出しはすべてこの配列を対象とする。パターン集は永続化しないため、再読み込みで失われる。残しておくには「パターン集を保存」でパターン集ファイルへ書き出し、「パターン集を読み込み」で戻す（4.4.6）。

#### 4.4.1 パターン番号の採番

パターン番号は配列上の位置から導出する。srName(i) は SR に位置 i を5桁ゼロ埋めした文字列を連結し、SR00000 から始まる連番となる。読み込んだファイル中の見出し番号は採番に用いない。これにより、複数のファイルを続けて読み込んでも番号が重複せず、常に通し番号が保たれる。

```js
const srName = (i) => "SR" + String(i).padStart(5, "0");
```

#### 4.4.2 削除とパターン番号の振り直し

パターン集からの削除は deleteEntry(i) に集約される。削除は取り消せないため、実行前に確認ダイアログを表示し、対象のパターン番号・寸法・繰り上がる件数を提示する。末尾を削除する場合は繰り上がりが生じないため、件数の予告は表示しない。編集モードでは、パターン選択窓の「削除」とメニューの一覧の「×」は無効にする（4.4.7）。

パターン番号は位置から導出されるため、1件を取り除くと以降の番号は自動的に1つずつ繰り上がる。これが番号の振り直しにあたり、欠番は生じない。たとえば SR00001 を削除すると、従来の SR00002 が新たな SR00001 となる。

読み込み直後に付与される「新規」の強調範囲も、削除位置に応じて追従させる。範囲より前を削除したときは範囲全体を1つ前へ移し、範囲内を削除したときは終端のみを縮める。範囲が空になった場合は強調を解除する。

#### 4.4.3 書き出し経路の一覧

| **形式**                     | **ファイル**           | **対象と単位**                                                                                                                                                                                           |
|------------------------------|------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| U-BOX（SRバイナリ）          | U-BOX.bin              | 全パターンを1ファイルへ収録（最大256件。超える場合は確認のうえ先頭256件）。制御4ビットを保持する                                                                                                         |
| PC10（パタコン）             | SRDS.zip               | SRDS.IDX と Dnnn/SRxxxxx.DAT（1ファイル＝1パターン）をZIP1本で（4.3.3）。制御4ビットを保持する                                                                                                           |
| SRテキスト                   | knit-patterns-SR.txt   | 全パターンを1ファイルへ収録（パターン集が空なら現在のパターン1件）。形式上、制御4ビットは保持されない                                                                                                    |
| SRテキスト（現在のパターン） | knit-pattern-SR.txt    | 編集中のパターン1件のみ（パターン集の内容に影響されない）。見出しは SR00000。2値のため多色は地色以外を X にし、その旨をトーストで知らせる。制御4ビットは保持されない                                     |
| JSON（現在のパターン）       | knit-pattern.json      | 編集中のパターンのみ。配色・制御4ビット（a を外した印を含む）を含む。種類 format="SilverReedPattern"・版 version・保存したアプリ app・保存日時 savedAt を持つ（4.4.8）。保存前に読み戻して一致を確かめる |

パターン集は単色・多色を問わず色番号グリッド（grid）とパレットで保持する（2.2）。U-BOX / PC10 への書き出しでは色数ぶんのパスへ展開し、読み込みでは色数フィールドから畳み込んで復元するため、3色以上でも往復で色が失われない（4.3.5）。ただし SRテキスト形式は2値のみのため、書き出すと地色以外は X に丸められる。制御4ビットを保持したい場合は U-BOX または PC10 を用いる。表示色や件数（U-BOX は256件まで）も含めてパターン集をそのまま退避・復元するには、パターン集ファイル（4.4.6）を用いる。

#### 4.4.4 登録件数の上限（MAX_LIB）

パターン集に登録できるパターン数は MAX_LIB = 3000 件までとする。SRDS.IDX の存在ビットマップは16384件ぶんの容量を持つため（4.3.6）、3000件は形式側の制約ではなくアプリ側の方針値である。上限に達したあとも書き出し経路は従来どおり動作し、SRDS.IDX の収録数 N には3000が入る。

上限は、パターン集へ追加されるすべての経路（パターン集ファイルの「後ろに追加」・SRテキスト・U-BOX・PC10 .DAT の読み込みと、「現在のパターンを追加」）で判定する。読み込みの共通処理 openImportedEntries が空き件数 free = MAX_LIB − 現在件数 を求め、読み込み件数が free を超える場合は確認ダイアログを表示する。ダイアログには現在件数・読み込み件数・合計・追加できる件数・保存できない件数を提示し、OK で先頭から free 件だけを追加し、キャンセルでは1件も追加しない。追加後にトーストで超過件数を再掲する。

すでに3000件に達している場合は、選択肢がないためOKのみの警告ダイアログとし、読み込みは行わない。「現在のパターンを追加」も同様に登録せず警告する。確認ダイアログは okOnly を指定するとキャンセルボタンを表示しない。

切り捨ては読み込んだ順の先頭からの採用であり、超過ぶんは黙って捨てない。件数表示はメニュー内の一覧見出しで「N / 3000件」と現在数と上限を並べて示す。

#### 4.4.5 縮小表示（SRThumb）

パターン選択窓の一覧には各エントリの縮小表示を並べる。SRThumb は図案を 76×76 ピクセルの枠に収まる大きさへ縮め、パレットの色で描く。枠より大きい図案は実数倍で縮小し、枠より小さい図案は整数倍に拡大して目の境界をくっきり保つ。

描画は1目ずつ fillRect するのではなく、出力の各画素から図案の目を最近傍で引いた ImageData を1回だけ置く。画面外のサムネイルは IntersectionObserver で見えてから描く（IntersectionObserver の無い環境ではすぐ描く）。3000件（60目×150段）の読み込みから一覧表示までは、以前の方式で約18秒、この方式で約3秒（うちテキストの解析が約2秒）であった（ヘッドレス Chromium での計測）。以前の方式は1目を1ピクセル未満にできず、76目または76段を超える図案は枠からはみ出して一部しか見えなかった。

#### 4.4.6 パターン集の保存と読み込み（全データ）

U-BOX・PC10・SRテキストへの書き出しは、形式の制約によって表示色（パレット）、件数（U-BOX は256件まで）、色（SRテキストは2値）などの一部を失う。パターン集をそのまま退避・復元するため、全エントリの全データを1つの JSON ファイルへ保存し、そのまま読み戻せる「パターン集ファイル」を用意する。操作は、ツールバーの全体表示（目）ボタンのすぐ左に並べたボタン、メニューの「パターン集を読み込み（全データ・JSON）」「パターン集を保存（全データ・JSON）」、パターン集ウィンドウ（PC の窓・スマホのシート）の見出しにあるボタンから行う。ツールバーとパターン集ウィンドウのボタンは、左から「現在のパターンをパターン集に追加」「読み込み」「保存」の順に並べ、ツールバーではその右にパターン集ウィンドウの表示・非表示を置く（表示ボタンはパターン集が1件以上のときだけ出す）。追加ボタンは登録先の番号をツールチップに示し、上限（3000件）に達しているあいだ無効にする。ツールバーの保存ボタンは、パターン集が空のあいだ無効にする。

パターン集への登録と保存は、ボタンの色で促す。今のパターンを編集すると（図案に何か描かれていて、パターン集に空きがあるとき）、「パターン集に追加」ボタンを緑にし、ツールチップとメニューの項目（「●未登録」）でも知らせる。編集ありの判定は、パターンを読み込んだ・新規にした・パターン集へ追加した時点の doc を覚えておき、doc がそれと別のものになったかで行う（元に戻すで戻した場合も編集ありのままとする）。パターン集から読み込んだ直後、新規にした直後、JSON を読み込んだ直後は色を付けない。パターン集に追加すると追加ボタンの色は消え、代わりに「パターン集を保存」ボタンを青にする（メニューは「●未保存」）。保存の促しは、パターン集ファイルを保存した・読み込んで置き換えた時点からパターン集が変わったとき（追加・取り込み・削除）に出し、保存するか、パターン集が空になると消す。色は、ツールバー、パターン集ウィンドウ（PC の窓・スマホのシート）の見出し、メニューの各所の同じボタンにそろえて付ける。

ファイルの構造は次のとおりである。1エントリを1行に書くため、差分の確認や目視での点検がしやすい。

```json
{"format":"SilverReedPatternLibrary","version":1,"app":"rev.28","savedAt":"2026-09-16T14:32:05.000Z","count":2,"memo":"6号針・中細2本どり\nゲージ 28目38段","entries":[
{"name":"SR00000","s":29,"r":14,"colors":2,"palette":["#FFFFFF","#000000", … 8色],
"grid":["0120120120…", … r本],"control":[4,4, … r個],
"passControl":[[4,2,6], … r個],"crc32":"1a2b3c4d"},
{"name":"SR00001", … }
]}
```

grid は r 本の文字列で、grid\[0\] が最上段（内部表現と同じ向き）、1文字が1目の色番号（"0"〜"7"）である。control は第1パス（デザイン段）の制御4ビット、passControl は段ごと・パスごとの制御4ビットで、全段が null のときは省略する。name は目で見るためのもので、読み込みでは位置から振り直す（4.4.1）。したがって置き換えで読み込むと、保存したときと同じパターン番号に戻る。

crc32 は、エントリを正規形（libNormalize：長さを目数・段数にそろえ、値を範囲に収め、表示色を大文字にしたもの）にしたうえで、目数・段数（各2バイト、リトルエンディアン）、色数、パレット8色の RGB、図案（段 × 目）、control（段数ぶん）、passControl（段ごとに長さ1バイト。null は 0xFF。続けて値）の順に並べたバイト列の CRC-32（多項式 0xEDB88320。4.3.7 と同じ）を、8桁の16進で表したものである。

保存では、まず保存名を尋ねるダイアログを出す（下記）。「保存」を押すと、書き出す文字列をいったん読み込み処理（parseLibraryJSON）に通して読み戻し、全件について全値が元のエントリと一致すること（libSame。チェックサムに頼らず値を比べる）を確かめてからダウンロードする。一致しない場合は保存せずに知らせる。ダウンロードはこの「保存」のクリック処理の中で発行する。パターン集が空のときはダイアログを出さず、登録を促す。

パターン集には、読み込み・保存したファイルの名前を結びつけて持つ（libName）。パターン集ファイルを空のパターン集へ読み込む、または置き換えで読み込むと、そのファイル名になる。後ろに追加で読み込んだときは、パターン集にまだ名前が無い場合だけそのファイル名を結びつけ、名前があれば追加先の名前を保つ。保存するとその保存名になる。パターン集が空になったら名前を消す。ほかの形式（SRテキスト・U-BOX・PC10）の取り込みは名前を変えない。

結びついたファイル名は、パターン集の上部に表示する。パターン集ウィンドウでは見出しのすぐ下、メニューではパターン集の一覧の上に、ファイルのアイコンと名前を1行で出す（長い名前は末尾を省略し、全体はツールチップで示す）。名前が無いときは表示しない。

保存名ダイアログの入力欄には候補名を入れておく。候補は、パターン集に結びついたファイル名があればその名前、無ければ knit-library-年月日-時分.json である。開いた時点で入力欄にフォーカスし、拡張子 .json の手前までを選択して、そのまま打ち替えられるようにする。Enter で保存、Esc（フォーカスの位置によらない）とキャンセルで閉じる。

保存名は libFileName で整える。前後の空白を除き、ファイル名に使えない文字（\\ / : \* ? " \< \> \| と制御文字）を「\_」に置き換え、末尾の . と空白を除き、拡張子を .json にそろえる（.json は省略でき、.JSON なども .json になる）。整えた結果が空ならエラーを表示し、100文字を超える場合もエラーとする。どちらもダイアログを閉じずに入力欄へ戻す。文字を置き換えたときは、保存後のトーストで知らせる。

ブラウザからの保存はダウンロードとして行うため、保存先はブラウザのダウンロード先になり、同じ名前のファイルがあると「(1)」などを付けた別名で保存されることがある。ダイアログにもその旨を示す。日本語のファイル名も使える。

保存名ダイアログには、ファイル名の下にメモの入力欄（textarea）を置く。メモはパターン集に1つ持ち（libMemo）、ファイル名と同じ扱いで、パターン集ファイルを読み込むと入り、保存するとその内容になる。すでにメモがあるときはその内容を入れて開くので、そのまま書き直せる。メモを消して保存すれば、メモの無いファイルになる。

入力欄の大きさは全角25字（LIB_MEMO_COLS）× 10行（LIB_MEMO_ROWS）ぶんで、幅は calc(25em + 20px)、高さは 10行 × 1.7em ＋ 余白とし、手で広げられないようにしている（resize なし）。それより長く書いたときは枠の中を縦にスクロールする。ファイルが際限なく膨らまないよう全体で 2000 文字（LIB_MEMO_MAX）までとし、超えた分は入力の時点で切る。入力欄の右上に「いま何文字／2000」を出し、上限に達したら色を変えて知らせる。メモの中では Enter は改行で、保存はしない（ファイル名の欄では Enter が保存）。

メモは libNormMemo でそろえてから書き出す。改行を \n にし、各行の行末の空白（半角・全角・タブ）と末尾の空行を落として上限で切る。保存と読み込みで同じ関数を通すため、書き出した文字列を読み戻すと必ず同じになる。保存前の読み戻し検査（libSame による全件照合）では、メモも一致することを確かめる。一致しなければ保存しない。

ファイルでは entries の前に "memo" として書く。メモが空のときはキーごと省く。version は 1 のままとする。memo を知らない版のアプリはこのキーを読み飛ばすだけで、パターンは今までどおり読めるためである（逆に、メモの無いファイルを読み込んだときはメモを空にする）。「後ろに追加」で読み込んだときは、パターン集にまだメモが無い場合だけそのファイルのメモを結びつけ、メモがあれば追加先のメモを保つ（ファイル名と同じ扱い。追加でメモを勝手に書き換えないため）。パターン集が空になったときは、ファイル名とともにメモも消す。

読み込んだメモは、パターン集ウィンドウとメニューの一覧の上部で、ファイル名の1行下に出す（libNameBar）。付箋のアイコンを添え、改行をそのまま見せ（whitespace-pre-wrap）、長いときはその枠の中を縦にスクロールする。窓の高さを図案の一覧に譲るため、見える高さは 4.8em（約4行）までとしている。メモが無いときは表示しない。読み込みの確認ダイアログとトーストでは、メモのあるファイルであることを「メモあり」と示す。

読み込みでは、まずファイル全体を判定する。JSON として読めない（途中で切れているなど）、format が違う、1パターンぶんの JSON（4.4.3 の knit-pattern.json）である、version が新しい、のいずれかであれば読み込まずに理由を示す。続いて各エントリを検査して正規形へそろえる。内容が読めないエントリ（目数・段数が範囲外、grid が無いなど）は飛ばし、範囲外や欠けた値は補正して読み込む。チェックサムが一致しないエントリとチェックサムの無いエントリは読み込むが、要確認として件数とファイル内の位置を示す。ファイルの count と実際の件数が違う場合もあわせて示す。

今のパターン集が空で要確認の項目も無ければ、確認なしで読み込み、「パターン集を N件読み込みました（チェックサム全件一致）」と知らせる。要確認の項目があるときは、その内容を示して読み込むかを確かめる。今のパターン集が空でないときは、件数と検査結果を示したうえで「置き換える／後ろに追加／キャンセル」の3択を出す（確認ダイアログは okLabel / altLabel で3択にできる）。置き換えは今のパターン集を消して保存時と同じ番号で復元するもので、元に戻せない。ファイルが MAX_LIB を超える件数を含む場合は、置き換えでも先頭 MAX_LIB 件までを採り、超えるぶんを確認時に示す。後ろに追加は他の形式の読み込みと同じ openImportedEntries を通り、上限 MAX_LIB（4.4.4）を超えるぶんは確認のうえ切り捨てる。読み込み後は、1件なら編集画面で開き、複数ならパターン集ウィンドウを開く。

メニューの「JSON読み込み（現在のパターン）」でパターン集ファイルを選んだ場合は、パターン集の読み込みへ回す。逆に、パターン集の読み込みで1パターンぶんの JSON を選んだ場合は、開くべきメニューを案内する。

往復の確認として、パターン集ファイルを保存し、アプリを読み込み直してそのファイルを読み込んだあとの SRDS の ZIP と U-BOX.bin の書き出しが保存前と1バイトも違わないこと、もう一度保存したファイルが保存時刻を除いて同一であることを確かめている。3000件（60目 × 150段、約33MB）での所要時間は、読み込みから一覧表示までが約2秒、保存（読み戻し検査を含む）が約2秒であった（ヘッドレス Chromium での計測）。

#### 4.4.7 編集モードでのコピーと貼り付け

編集モードでは、パターン選択窓とメニューの一覧の各パターンのボタンを、「読込」から「コピー」に替える。コピーはそのパターンの図案をクリップボードへ写し、そのまま配置（ゴースト）にする（copyEntryToGhost）。位置はドラッグで決め、「選択・配置」パレットの「確定」（または Enter）で貼る。左右反転・上下反転・回転もゴーストのまま行える。クリップボードにも入るので、ペーストで同じパターンを何度でも貼れる。狭い画面では、コピーするとパターン集のシートを閉じて図案を見せる。

初期位置は画面の中央付近で、左端・最下段の外へは出さない。パターンのほうが貼り先より大きいときは、左端・最下段にそろえて右と上へはみ出す位置に置く（確定時に広げられる）。置いた直後は、ゴーストが見える位置までスクロールする。目数・段数の外へはみ出して確定したときは、警告して目数・段数を広げてから貼る（3.3）。

貼るのは図案（色番号）だけで、制御4bitは写さない。色は色番号のまま貼り、表示色は貼り先のパレットに従う。地色（色0）のマスも地色として貼る（ゴーストの矩形の中は、貼り先の図案を置き換える）。

コピー元と貼り先の色数（色パス数）は一致していなければならない。色数が違うとパスの数と色の割り当てが変わり（2色は1パス、3色以上は色数ぶんのパスで最終パスが地色。4.3.5）、貼った部分が意図どおりに編めないためである。コピーを押した時点で、コピー元の色数（エントリの色数と図案が使う最大の色番号の大きいほう）と貼り先の色数を比べ、違えば警告を出してコピーしない（配置もクリップボードへの写しもしない）。警告には両方の色数を画面上部の「色数」と同じ表記（「3色／3パス」「2色(レース)／1パス」）で示し、先に貼り先の「色数」をコピー元に合わせてから、もう一度コピーするよう案内する。色数は自動では変えない。

パターン集からコピーした配置とクリップボードは、コピー元の色数と名前を持つ。配置したあとで貼り先の色数を変えた場合は、「確定」の時点で同じ確認をし、一致しなければ貼らずに配置を残す（色数を合わせてから確定し直せる）。クリップボードからのペーストも、一致しなければ置かずに警告する。図案の中で選択した範囲のコピー・カット・移動は同じパターンの中の操作なので、この確認の対象にしない。

編集モードでは、パターン選択窓とメニューの一覧の「DAT」（1パターンの SRDS 書き出し、4.3.3）と「削除」（一覧では「×」、4.4.2）を無効にする。パターンを組み合わせている最中に、パターン集そのものを誤って書き出したり消したりしないためである。表示モードに戻せば、従来どおり「読込」「DAT」「削除」が使える。転送中は、読込と同じくコピーも押せない（5.4）。

#### 4.4.8 ファイル形式の版（version）

パターン集ファイル（format="SilverReedPatternLibrary"）と現在のパターンの JSON（format="SilverReedPattern"）は、共通の整数の版 version を持つ。読み込みの判定には version だけを使い、あわせて書く app（保存したアプリの版表記 APP_REV、例 "rev.28"）は記録と案内のためのもので判定には使わない。現在のパターンの JSON には rev.28 から format・app・savedAt（保存日時）を書く。

保存は、中身に必要な最も低い版で書く（fileVersionFor）。いまは、a を外した印（CTRL_A_OFF）を使った段が1つでもあれば v2、無ければ v1 である。ふだんのファイルは v1 のままなので、古いアプリでもこれまでどおり読める。現在のパターンの JSON は、保存前に読み戻して図案と制御が一致することを確かめ、一致しなければ保存しない（パターン集ファイルは従来から読み戻し検査をしている）。

読み込み（fileVersion）は次のとおりとする。version が無いファイルは v1 として読む（rev.27 までの現在のパターンの JSON は format を持たないので、format が無く図案がある JSON は v1 のパターンとして読む）。このアプリより新しい版は読まず、「新しい版のアプリで保存されたファイルです（ファイル v3・rev.40 で保存／このアプリ rev.28 は v2 まで）。アプリを更新してから読み込んでください」のようにダイアログで理由を出す。今のパターン・パターン集は変えない。version が整数でない・1 未満のときも読まない。format が知らない値のときは「別の種類のファイルです」として読まない。古い版は FILE_UPGRADE の変換を1段ずつ通して今の形にしてから読む（v1→v2 は中身が同じなので変換しない）。読み込んだときのトーストとパターン集の確認ダイアログには、ファイルの版と保存したアプリ（「v2・rev.28 で保存」、版の無い旧形式は「v1・旧形式」）を出す。

版を上げるのは、古いアプリで読むと中身が壊れる・意味が変わる変更のときだけとする。古いアプリが無視できる項目を足すだけ（パターン集のメモ、app・savedAt など）なら上げない。版を上げたときは、次の表に行を足し、FILE_VERSION と FILE_UPGRADE を更新する。なお rev.23〜27 は a を外した印を含んでも version 1 と書いていたため、v1 のファイルでも control の 0〜31 を正として受け付ける。

| **版** | **中身**                                                                      | **書く条件・旧アプリでの扱い**                                                                     |
|--------|-------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| v1     | これまでの形式。制御4ビット control は 0〜15                                  | a を外した印を使っていないとき。version の無いファイルも v1 として読む                             |
| v2     | control に多色の色1パスの a を外した印 CTRL_A_OFF（bit4 = 16）を含む（0〜31） | a を外した段が1つでもあるとき。rev.27 以前のアプリはパターン集ファイルを「新しい版」として読まない |

旧アプリとの関係: rev.27 以前のアプリは、パターン集ファイルでは version が 1 より大きいと「新しい版」として読まないので、v2 のファイルを壊さない。現在のパターンの JSON は版を見ないので読むが、a を外した印は表示に使われるだけで、転送と書き出しには影響しない（rev.24）。

### 5.2 パターン変換

変換は「内容を書き換える変換」と「フラグとして機器へ伝える変換」の2種に分かれる。

パス数 P は passCount() が与える。地色を除く色数 c は、設定した色数（doc.colors）と図案が実際に使っている最大の色番号の大きいほうを採り、c ≦ 1 なら 1パス、c ≧ 2 なら c + 1 パスとなる。最終パスは地色の柄である。

| **変換**   | **関数**  | **分類** | **効果**                                                                                                   |
|------------|-----------|----------|------------------------------------------------------------------------------------------------------------|
| 反転       | cgInvert  | 内容変換 | 0と1を入れ替える。2色（1パス）のときだけ有効。多色ではパスと色の対応が壊れるため受け付けず、理由を表示する |
| 左右反転   | bmHflip   | 内容変換 | 各段の並びを反転する                                                                                       |
| ミラー     | bmMirror  | 内容変換 | 各段に自身の逆順を連結。目数が 2n になる                                                                   |
| シェブロン | bmChevron | 内容変換 | 各段に逆順の2要素目以降を連結。目数が 2n−1 になる                                                          |
| 縦2倍      | bmVscale  | フラグ   | アプリ側では表示・送出とも等倍。機器側で展開する                                                           |
| 横2倍      | bmHscale  | フラグ   | 同上                                                                                                       |

内容変換の適用順序は kcDeriveColor() により固定されている。反転 → 左右反転 → 折返し（0=オリジナル／1=ミラー／2=シェブロン）の順である。順序が変わると結果が異なるため、この順序は機器側実装と一致させる必要がある。内容変換の経路はこの関数だけで、反転は2色（1パス）のときにしか適用しない。多色でパスと色の対応が壊れるのを防ぐため、反転ボタン自体も passN \> 1 では受け付けず、理由を表示して何も変えない。

```js
const kcDeriveColor = (base, invert, hflip, fold, n) => {
let p = base;
if (invert && n <= 1) p = cgInvert(p); // 反転は2色(1パス)のときだけ
if (hflip) p = bmHflip(p);
if (fold === 1) p = bmMirror(p);
else if (fold === 2) p = bmChevron(p);
return p;
};
```

送出目数は width × hx、送出段数は rows × vx で算出される。送出目数が MAX_S（240）を超える場合は警告を表示し、スタートを禁止する。

### 5.3 keyFlags のビット割当

適用中の変換を1バイトのビットフラグにまとめ、MODE_ENTER と ROW_DATA の両フレームに含めて送信する。この割当はアプリと機器ファームウェアで一致していなければならない。

| **ビット** | **値** | **変換**               |
|------------|--------|------------------------|
| bit0       | 0x01   | 反転                   |
| bit1       | 0x02   | 左右反転               |
| bit2       | 0x04   | ミラー（折返し=1）     |
| bit3       | 0x08   | シェブロン（折返し=2） |

### 5.4 転送中のパターンロック

転送は MODE_ENTER で目数と段数を宣言したうえで ROW_DATA を1段ずつ流す方式である。したがって転送中にパターンが差し替わると、機器がすでに受理した寸法と以後の段データが食い違う。段数が減る差し替えでは内部添字が範囲外となり、フレーム組み立てが例外で失敗して転送が無言で停止する。これを防ぐため、転送中はパターンを変更する操作をすべて禁止する。

#### 5.4.1 転送状態の引き上げ

転送状態 running は編み機コントロールの内部状態であるため、そのままでは編集側から参照できない。onRunningChange により親コンポーネントへ引き上げ、knitBusy（描画用の状態）と knitBusyRef（判定用の同期ミラー）の両方で保持する。判定に ref を用いるのは、commit() が React の再描画を待たずに最新の転送状態を参照する必要があるためである。

```js
useEffect(() => { onRunningChange?.(running); }, [running, onRunningChange]);
useEffect(() => () => { onRunningChange?.(false); }, [onRunningChange]);
```

2つ目の効果はアンマウント時の解除である。編み機モードを閉じたときに転送状態が真のまま残るとロックが解けなくなるため、アンマウントで必ず偽を通知する。

#### 5.4.2 二段構えの防御

防御は関門と画面表示の二段で構成する。実際にデータを守るのは関門であり、画面表示は操作者に理由を示すためのものである。

| **層**           | **内容**                                                                                                                                                                                                            |
|------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 関門（実防御）   | busyBlocked() を commit() / undo() / redo() の先頭に置く。真のときは即座に復帰し、「編み機へ転送中です。ストップしてからパターンを変更してください」を通知表示する                                                  |
| 画面表示（提示） | パターンを変える操作を disabled とする。パターン集およびメニューの読込・コピー、目数・段数の入力と適用、undo / redo、SRテキスト・U-BOXカード・JSON の読み込み、全消去。メニュー冒頭には転送中である旨の帯を表示する |

書き出し操作（PC10 .DAT、U-BOX、SRテキスト、パターン集ファイル、図案PNG、機械用PNG、JSON）は doc を変更しないため、転送中も有効のままとする。読み込み操作（パターン集ファイルを含む）のボタンは転送中は無効にする。編み機コントロール内の変換操作（反転・左右反転・ミラー・シェブロン・縦2倍・横2倍・送り方向）は従来どおり running により個別に禁止される。

#### 5.4.3 ロックの解除条件

次のいずれかで running が偽となり、ロックは自動的に解除される。ストップ操作、接続の切断（操作者による切断と転送中の切断の双方）、NAK の受信、READY 応答のタイムアウト、および編み機コントロールの終了。

ベッドの絵は要素の幅を ResizeObserver で測り（useWidth）、実寸の座標で SVG を描く（文字が伸び縮みしないため）。狭い画面では、ベッドは次に編む段の下へ回り込む。表示範囲は選針区間とカーソルを含む範囲に余白を足したもので、範囲の外にいるキャリッジは端に寄せて描く。STATUS は針カウントや位置の更新で頻繁に届くため、通信ログには段階・不一致・警告が変わったときだけ記録する。接続し直したとき・切断したときは機器の版と STATUS を消す（模擬サーバの古い状態を残さない）。

空通しで検知したカーソル（rev.34 の機器。STATUS \[27..39\]）は、状態の行に「カーソル検知 往路← 0 ／ 復路→ 0」のように出す（kcCurText）。往路・復路それぞれ、最初に検知したカーソルを 0 とし、2 つめ以降はそこから進行方向へ何目あとか（INP の数）を「0, +1目」のように並べる。スタート・反転時のパルスは含まない。矢印は動かした向きで、右端から始めたなら往路が ←、復路が →。往復とも 1 つずつなら正常で灰色、2 つ以上か 5 つ以上（4 つまで出して「…」）なら赤で出す。+1 目のように隣り合っていれば同じパルスを二度数えた疑い（6.9.2）、離れていればカーソルが本当に 2 つある（機器はカーソル 1 つだけに対応する）。空通し待ち〜空通し完了の段階で出し、編み込み中と、まだ 1 つも検知していないときは出さない。STATUS が 40 バイト未満の機器（rev.33 まで）では出さない。

#### 6.3.4 プロトコル版（v2 / v3）と後方互換

v2 は多色編み（4.3.5）のための拡張であり、v1 のフレームの末尾へ追記するだけの構成とした。v1 のファームウェアは MODE_ENTER の \[6\] 以降と ROW_DATA の目ビット列より後ろを読まないため、そのまま動作する（多色の区別はできない）。v2 のファームウェアは追記の有無をフレーム長で判定し、MODE_ENTER が 6 バイトなら N = 1・パレットなし、ROW_DATA に追記がなければ段位置からパス番号を求める。アプリは常に v2 で送り、READY の版は参照しない。

ROW_DATA のパス番号・色番号は、アプリの expandPassRows の結果（tx.pass / tx.color）をそのまま送る。ファームウェアは送出段の添字 i と送り方向 dir から、k = i mod N、パス番号 = dir が 0 なら N − k、1 なら k + 1、色番号 = passColorNo(パス番号, N) を求め、受信値と照合する。段+ では段内のパスを逆順に積むため（6.5.1）、どちらの送り方向でも送出はパス1から始まる。デザイン段の内部添字は i ÷ N（整数部）、表示段番号はデザイン段数 − i ÷ N である。

```text
NAK [3] エラーコード
1 ROW_DATA 破損・範囲外（目数 1..240 外、添字 ≧ 段数、長さ不足）
2 MODE_ENTER 不正（N が 2 または 9 以上、段数が N の倍数でない、
段数 > 1000 × N）。段番号フィールドは 0xFFFF
3 ROW_DATA のパス番号・色番号が段位置から求めた値と一致しない
4 空通しが済んでいない（v3 の機器だけ。6.9.3）。編み込みに入れない
```

いずれの NAK もアプリは転送を停止してエラーを表示する（6.5.2）。表示にはエラーコードと段番号（0xFFFF は MODE_ENTER に対する NAK）を添え、通信ログにも「NAK code n」として残す。コード 3 は、アプリとファームウェアでパスの並びの解釈が食い違ったまま、違う糸で編み進めることを防ぐための照合である。

v3 はキャリッジ制御（6.9）のための拡張で、既存のフレームは変えずに CALIB（0x04）と STATUS（0x84）を足した。機器は READY \[1\] で版を知らせ、アプリは版 3 以上の機器にだけ CALIB を送り、空通しが済むまでスタートさせない（5.5）。表示専用の機器（CARRIAGE_ENABLE = false や対応外の機種）は版 2 を返し、CALIB を無視し STATUS を送らないので、v3 のアプリとも従来どおりに動く。v2 のアプリは STATUS を知らないタグとして読み捨てるが、空通しをしないため v3 の機器では NAK code 4 で止まる。

rev.36・rev.37 では版を変えずに BYE（0x05、C → S）と切断要求（0x85、S → C）を足した。古い機器は BYE を知らないタグとして無視する。古いアプリは切断要求を読み捨てるので、M5キャリコンは 1 秒（KICK_WAIT_MS）後に自分から切る。ただし rev.36 のアプリは BYE のない切断で自動的につなぎ直すため、A・C の同時長押しで切るには rev.37 のアプリを使う。rev.36 の機器が送っていた READY の \[2\]（機能ビット）と 2 秒ごとの STATUS は rev.37 で取りやめ、READY は 2 バイトに戻した（rev.36 のアプリは READY \[2\] がなければ応答途絶を監視しないので、rev.37 の機器を誤って切らない）。

#### 6.3.5 CALIB（2バイト、v3）

```text
[0] 型タグ 0x04
[1] 空通しの開始側 0 = 右端（往路は左へ） / 1 = 左端（往路は右へ）
```

機器は空通しを最初からやり直す。送信中なら編み込みを止め、開始側を NVS に保存し、LCD と音声で「キャリッジを右端に置いて、左へ空通ししてください」等を案内する。応答は STATUS（段階 1）。

機器は、段階・位置・向き・理由・区間などが変わったときと MODE_ENTER／CALIB／STOP の応答のあとに STATUS を送る。針カウントとキャリッジの針位置だけの変化は 0.25 秒に 1 回までに間引く（空通しで検知したカーソル \[27..39\] の変化は間引かずにすぐ送る）。宛先は最後に MODE_ENTER／CALIB／ROW_DATA／STOP を送ってきたクライアント（探索のプローブには送らない）。

rev.31 の機器は 24 バイトで送る。アプリは 24 バイト以上を受け付け、27 バイト未満ならキャリッジの針位置を不明として端に描く。針位置は ce::Engine の q（6.9.4）で、トラバースの始め（ICD の切り替え）で不明に戻り、最初の IPC の変化かカーソルで分かる。止まったあとも次のトラバースが始まるまで最後の位置を保つ。

\[27..39\] は空通しの往路・復路で検知したカーソル（6.9.3）で、スタート・反転のパルス（IN1_GUARD 未満）は含まない。記録は空通しを始めたとき（CALIB・A ボタン）と往路を始めたときに消すので、不一致で空通し待ちに戻ったあとも、次の往路を始めるまでは前回の検知を送り続ける。カーソルは 1 パスに 4 つまで記録し、それより多いときは bit6／bit7 を立てる（不一致の理由にも「記録があふれた」128 が立つ）。rev.32〜rev.33 の機器は 28 バイトで送り（\[27\] は 0）、アプリは 40 バイト未満ならカーソル検知を出さない。

### 6.4 目ビットのパッキング

ROW_DATA の目ビット列は、左端の目（目1）を bit0 とする直列化を行う。各バイトは LSB から MSB の順に詰め、1 がマークを表す。この向きは U-BOX／PC10 バイナリ（4.2.3、左端 = byte0.bit0）と同一であり、ファイル出力とライブ転送で目の向きが一致する。

```js
function kcPackRow(row) {
const n = row.length;
const b = new Uint8Array(Math.ceil(n / 8));
for (let i = 0; i < n; i++)
if (row[i]) b[i >> 3] |= 1 << (i & 7); // 目i（左端=0） → bit i
return b;
}
```

row\[i\]（左端 = 添字0）を bit i へ写像するため、左端の目が最初のビット（byte0.bit0）となり、右へ向かって bit1, bit2 … と進む。ファームウェア側もこの向き（左端 = bit0）で展開する。

デバッグ表示用の kcBits() は、送出済みバイト列から表示順（左→右）の文字列を復元する。bit0 が左端に対応するため、ビット順をそのまま左から並べればよい。送信データが意図した図案と一致しているかの目視確認に用いる。

### 6.5 転送シーケンス

転送は ACK 駆動のパイプラインである。1段の送信に対する ACK 受信が次段の送信契機となるため、機器側の処理速度に自動的に追従する。

```text
クライアント 機器（M5Stack）
│ │
│──── MODE_ENTER(w, rows, kf) ──────▶│
│ │ 受入準備
│◀─────────── READY ─────────────────│
│ │
│──── ROW_DATA(cursor) ─────────────▶│
│ │ 編成・給糸
│◀─────────── ACK(cursor) ───────────│
│ cursor を送り方向へ1段進める │
│──── ROW_DATA(next) ───────────────▶│
│ （以降ループ） │
│ │
│──────────── STOP ─────────────────▶│
│◀────────── STOPPED ────────────────│
```

キャリッジ制御の機器（v3）では、ACK は受け取ったパスでキャリッジが最後の選針区間を抜けたときに返る（縦2倍は 2 回目）。アプリはすぐ次のパスを送り、機器はキャリッジが折り返して次の選針区間に入るまでにそれを受け取る。届く前に区間に入るとそのトラバースは平編みになり、音声で知らせる（6.9.4）。

#### 6.5.1 段送りと周回

送り方向 dir が 0（段+）のとき表示上の段番号は +1、1（段−）のとき −1 で進む。表示段N と内部添字 i は N = R−i の関係にある（2.2 参照）ため、内部添字は 段+ で −1、段− で +1 へ動く。編成の先頭段は、段+ なら段1（内部添字 R−1）、段− なら段R（内部添字 0）である。送り方向の初期値は段+ とする。終端に達すると反対端へ折り返し、周回カウンタ loops を1増加させる。連続した編成を無限に継続できる。

画面は段1が最下段であるため（8.1 参照）、段+ は編み進むほどカーソルが上へ移動する。画面上の見え方に合わせ、操作段のボタン表記は段+ を「上向き（段+）」、段− を「下向き（段−）」とする。開始段の手動送りに用いる矢印も送り方向に連動させ、段+ では送るが▲・戻すが▼、段− ではその逆となる。移動の単位は送出段（パス段）1つである。したがって多色（3色以上）では同じデザイン段の中をパスごとに動かせ、「段5 パス2/3」のように途中のパスから編み始められる。2色（1パス）ではデザイン段と送出段が一致するため、従来どおり1段ずつ動く。以前はデザイン段単位（パス数ぶん）で動かし、開始段を必ず第1パスの段へスナップさせていたが、途中のパスから編み直せないため取りやめた。パス番号・色番号は送出段の添字と送り方向から決まり（6.3.4）、機器側も同じ式で照合するので、どのパスから始めても食い違いは起きない。端では折り返さず範囲内にとどめ、周回は転送中の ACK 駆動側で行う。「1段目」に戻す操作と送り方向の切り替えは、いずれも先頭段（段+ なら段1・パス1）へ置き直す。なお 6.3 のフレーム \[5\] および付録B の機器ニブルにおける「下送り／上送り」は機器側の呼称であり、変更しない。

スタートのたびに ready を偽へ戻し、MODE_ENTER から再ハンドシェイクを行う。これにより機器側の状態と確実に同期する。ストップ時には現在の開始段（cursor）を保持するため、再スタートで中断位置から継続できる。

#### 6.5.2 無応答とエラーの扱い

READY と ACK は待ちの性質が異なるため、扱いを分ける。READY は機器が MODE_ENTER を受理して即座に返すものである。したがって既定 3000ms（KC_READY_TIMEOUT_MS）を過ぎても届かない場合は、機器が存在しないか応答していないと判断し、転送を停止してエラーを表示する。この場合 STOP は送出しない。

ACK は1段を編み終えた合図であり、キャリッジを手で操作する間ずっと待つのが正常である。したがって時間で打ち切ってはならない。代わりに応答待ちの経過時間を表示し、5000ms（KC_WAIT_SHOW_MS）を超えると「応答待ち NN秒」を画面に出し、30000ms（KC_WAIT_ALERT_MS）を超えると警告色へ変える。停止するかどうかは操作者が判断する。

NAK を受信した場合は以降 ACK が来ないため、転送を停止してエラーを表示する。確立済みの接続が転送中に切断された場合、および操作者が切断を行った場合も同様に転送を終了する。いずれも転送状態（running / pending）を確実に解除し、画面が転送中のまま残らないようにする。

確立済みの接続が利用者の操作によらずに閉じたとき（ネットワーク等）は、状態を「切断」にし、転送中なら転送を終了する。自動ではつなぎ直さず、応答の途絶も監視しない（rev.36 で入れた 10 回の再接続・6 秒の監視・「再接続中」「ネットワーク障害」の表示は rev.37 で取りやめた。糸処理などで長く待っても再接続を促す表示は出ない）。

利用者の切断（「切断」ボタン、「閉じる」によるアンマウント、ページを離れるときの pagehide）では、閉じる前に BYE を送る。M5キャリコンから切断要求（0x85）を受けたときは、BYE を返して閉じ（転送中なら転送を終了する。M5キャリコンが先に編み込みを止めているので STOP は送らない）、編み機コントロールを閉じてパターン表示モードに戻り（編集モードだったときも表示モードにする）、「M5キャリコンから切断されました。パターン表示に戻りました」と出す（handleFrame → disconnect → onDeviceBye。rev.37）。

ACK は待っている段のものだけを受理する。受信した段番号が送信済みで未応答の段と一致しない場合（重複した ACK、遅延した ACK、停止後に届いた ACK）は破棄し、通信ログに「ACK n 無視」として記録する。これにより段が飛ぶことを防ぐ。この判定は、ファームウェアが受信した段番号をそのまま返すことを前提とする（10章参照）。

段の送出前には内部添字が実在するかを確認する。範囲外であった場合はフレームを組まず、転送を失敗として停止し、添字と総段数をエラーに表示する。転送中のパターン差し替えは5.4 のロックで禁止しているが、二重の備えとして例外による無言の停止を防ぐ。

```js
if (!pat[idx]) {
failRun(`段の取得に失敗しました(添字${idx} / 全${pat.length}段)。`);
return;
}
```

### 6.6 模擬サーバ

実機が接続されていない場合、デバッグ有効時に限り模擬応答を生成する。MODE_ENTER には 150ms 後に READY（版 3）と STATUS を、ROW_DATA には設定秒数後に ACK を、STOP には 100ms 後に STOPPED を返す。実機接続が成立した時点で模擬サーバは自動的に無効化される。

模擬サーバはキャリッジ制御の機器として振る舞う。CALIB には、空通し待ち → 往路（0.5 秒後）→ 復路（1.1 秒後）→ 空通し完了（1.7 秒後。選針区間 −12〜+11、先行 0）の STATUS を返す。デバッグで模擬サーバを選ぶと v3 の機器として扱い、空通しが済むまでスタートを押せない（5.5）。ROW_DATA には編み込み中の STATUS を返し、キャリッジの針位置を区間の手前から向こう側まで 4 回に分けて動かし、ACK と同時に反対側の端へ着いて次は逆向き、とする。STOP には空通し完了の STATUS を返す。空通しでは、復路に移るときに往路のカーソル 1 つ、完了のときに往路・復路とも 1 つ（「0」）を、空通しで検知したカーソル（6.3.6 \[27..39\]）として返す。

### 6.7 ファームウェアの多色編み処理（KnitCtrl_M5.ino）

KnitCtrl_M5.ino はプロトコル v3 に対応し、M5Stack Core2 と CoreS3（CoreS3 Lite・SE を含む）では実機のキャリッジを読んで選針する（6.9）。多色パターンはパス単位で受け取り、そのパスを編み終えてから（縦2倍なら 2 回ぶん）ACK を返す。ACK の段番号は受信値をそのまま返す。対応外の機種と CARRIAGE_ENABLE = false のときは表示専用（版 2）として動き、受け取ったら即 ACK を返す。

段数の上限 MAX_ROW（1000）はデザイン段の上限として扱い、送出段の添字は 1000 × N 未満まで受理する。旧版は添字 1000 以上を NAK としていたため、334 デザイン段以上の3色パターン（1002 段以上）が途中で停止していた。

縦2倍（keyFlags 0x10）は、受け取ったパスを2回続けて編んでから ACK を返す。1パスでは同じ段を2回、多色ではパス1を2回、パス2を2回…パスNを2回の順となる。パスの並び（パス1→パスN）とパス番号・色番号の照合（6.3.4）は縦2倍でも変わらない。パスバッファは LCD の合成図を組み立てるために、編成中のデザイン段で受け取ったパスを保持する。寸法・パス数・keyFlags が変わった MODE_ENTER、およびパス1または別のデザイン段を受け取ったときに貯め直す。

LCD の下部は、デザイン段を1本の帯として、受け取ったパスを重ねた合成図（編み上がりの見た目）を描く。1 目は 1 マークで、マークの大きさは目数で決める。160 マークまでは 2×2 px、161 マーク以上は全体が画面に入らないため 1×1 px に落として 320 マークまで表示する。横2倍では 1 目を 2 マークで描くので、この判定も 2 倍したマーク数で行う（例: 90目の横2倍 = 180 マーク → 1×1 px）。帯の高さは 1 マーク、縦2倍では 2 マークである。収まるときは中央寄せ、1×1 px でも入りきらない場合（240目の横2倍 = 480 マーク）だけ右側を切り、帯の右端に橙の印を付ける。

多色（3色以上）の目は、アプリが MODE_ENTER で送ってきたパレットの糸色でそのまま塗る。色番号0（地色）も同じで、最終パスで選針された目とどのパスにも選ばれなかった目の両方が地色になるため、地色そのものを塗る。以前は地色を暗くして敷いていたが、これは「そのパスでは編まない目」の表し方であって、編み上がりの色ではないため取りやめた。まだどのパスも受け取っていない目だけは塗らず、背景の黒を残す。2色（1パス）も同じパレットで塗り、選針目を色1、非選針目を地色（色0）とする。アプリの既定パレットは地色が白・色1 が黒なので、既定では白地に黒マークとなる。以前は選針目を青（#2060FF）、地の目を黒の固定色で描いていたが、アプリで配色を変えても反映されないため取りやめた。パレットを受け取れなかった場合（v1 クライアント）は内蔵の既定色を使い、これもアプリの DEFAULT_PALETTE と同じ（色0 = 白 / 色1 = 黒）なので白地に黒マークになる。

暗い糸色の持ち上げは多色（3色以上）のときだけ行う。多色はデザイン段の途中で「まだ受け取っていない目」が背景の黒のまま残るため、黒に近い糸色（アプリの既定パレットでは色1 が \#000000 である）をそのまま塗ると見分けが付かない。輝度が 56 未満（MIN_LUMA）の色だけ、色相を変えずに輝度 56 相当まで持ち上げてから描く。2色（1パス）は1段を受け取った時点で帯のすべての目が地色かマークで塗られ、受信前の目が残らないため持ち上げず、送られてきた色をそのまま出す（既定なら白地に真っ黒のマーク）。2色でも持ち上げる場合は LIFT_ALWAYS を true にする。パレットを受け取れなかった場合（v1 クライアント）は内蔵の既定色を使い、どちらであるかを状態表示の PAL:APP ／ PAL:DEF で示す。あわせて現在のマークの大きさ（2px ／ 1px）も表示する。

帯はパスバッファから組み立てるため、停止→再開で表示がクリアされても同じデザイン段の受信済みパスから復元できる。

画面右上には、いま編むパスの糸色見本（P番号/N と COLOR n または GROUND）と、パス順に並べた色チップ（現在パスを黄枠）を表示する。左側には色数・パス数、デザイン段番号（段1 = 最下段）とパス、送出段の添字と送り方向、制御4ビットと指示記号（付録B。＊は \* で代用）、keyFlags を表示する。糸色が変わるパスで短く鳴らす BEEP_ON_COLOR_CHANGE（既定 false）を設ける。

rev.31 で画面を、ヘッダ（16px：IP・ポート・ホスト名・接続数・空通しの開始側 R/L）、案内（102px：日本語の案内、6.9.5）、パターン（120px：上記の合成図）に分けた。rev.38 で、案内を 142px、パターンを画面の下 1/3 の 80px（CoreS3 は 56px）にした（1 マーク 2×2 px で 40 段、1×1 px で 80 段が見える。縦2倍はその半分）。糸色見本と色チップは、編み込み中の案内の右上に出す。制御4ビットと keyFlags は案内の下端に 1 行で出す。表示専用のときは案内の位置に従来の状態表示を出す。

目ビットの展開は 6.4 に合わせて左端 = bit0（STITCH_BIT0_AT_RIGHT = false）とした。旧版は右端 = bit0 で展開しており、アプリの図案と左右が逆に表示されていた。

### 6.8 ファームウェアの WiFi 設定（SD カード／設定ポータル）

接続先の SSID・パスワードはソースに書かず、コンパイル後に SD カードまたは設定ポータルで設定する。接続候補は次の2つで、この順に試す。

```text
① 本体に保存した接続先（NVS。設定ポータルで保存したもの。あるときだけ）
② SD カードの /wifi.cnf。ないとき・形式が不正なときは
既定の SSID "SilverReed" ／ パスワード "12345678"
```

wifi.cnf は平文のテキストで、1行目が SSID、2行目がパスワードである。行末の CR／LF と先頭の UTF-8 BOM は取り除き、それ以外（空白を含む）はそのまま使う。2行目がなければオープンネットワークとする。SSID が 1〜32 バイトでない、またはパスワードが 8〜63 文字でない場合は形式不正とする。SD カードは M5Unified のピン情報（sd_spi\_\*、無ければ CS = GPIO4）で SPI 接続し、読み終えたら SD.end() で解放する。

```text
MyHomeWiFi
mypassword123
```

wifi.cnf の内容を書き換えた場合は、書き換えた内容を優先する。本体は wifi.cnf の SSID とパスワードから求めた指紋（FNV-1a）を NVS（キー sdsig）に記録し、起動時に前回と異なっていれば NVS の接続先（ssid / pass）を消去する。ホスト名は消去しない。したがって「最後に設定したもの（ポータルでの保存か wifi.cnf の書き換え）」が使われる。改行コードや BOM の違いだけでは書き換えとみなさない。

接続は1回あたり 6 秒（WIFI_TRY_TIMEOUT_MS）待ち、5 回（WIFI_TRIES）試す。候補が2つのときは①と②を交互に試す。5 回試しても接続できなければ設定ポータルに入る。起動中の LCD には SD の状態（no SD card／no wifi.cnf／wifi.cnf OK／wifi.cnf invalid）、試行回数と候補（NVS／SD／DEFAULT）、SSID を表示する。

設定ポータルには、上記の接続失敗のほか、起動時に A ボタンを押しているとき、動作中に C ボタンを 2 秒長押ししたとき、USB シリアル（115200bps）へ setup を送ったときにも入る（後の2つは転送中 RUN を除く）。ポータルでは本体が WPA2 のアクセスポイント KnitCtrl-XXXX（XXXX は MAC アドレス由来）となり、起動ごとに変わる 8 桁のパスワードと、そのまま接続できる QR コード（WIFI:T:WPA;S:…;P:…;;）を LCD に表示する。DNS をすべて本体（192.168.4.1）へ向けるキャプティブポータルとし、未知の URL（OS の接続確認を含む）は設定ページへ 302 で転送する。

設定ページには、本体に保存した接続先と wifi.cnf の状態、および候補の優先順を表示する。周辺のネットワークを検索した一覧（同名は1件、ステルスは除外、オープンは明示）から SSID を選ぶか直接入力し、パスワードとホスト名を入れて保存すると、NVS（名前空間 knitctrl、キー ssid / pass / host）に保存して 1.5 秒後に再起動する。入力の検証は SSID 1〜32 バイト、パスワード 8〜63 文字、ホスト名は英小文字・数字・ハイフン 1〜32 文字（前後の空白を除き小文字化）とする。保存済みのパスワードはページに出さず、同じ SSID でパスワード欄を空のまま保存したときは保存済みの値を維持する。「パスワードなし（オープン）」、「ネットワークを再検索」、「設定を消去」（NVS をすべて消去）も備える。SSID 等の表示はすべて HTML エスケープする。

ポータルでは A ボタンで直ちに再起動して接続を再試行する。端末が接続していない状態が 5 分（PORTAL_IDLE_RESTART_MS）続いた場合も再起動して再試行する。停電復帰時にルーターより先に本体が起動してポータルに入っても、自動で復帰させるためである。

保存したホスト名は WiFi のホスト名、mDNS 名、探索応答 INFO（0x90、7.1）のホスト名に用いる。複数の編み機コントローラーを置く場合は、ここで別々の名前を付けてアプリの機器一覧で区別する。rev.31 で日本語フォント（efontJA_16）とキャリッジ制御・音声を加えたため、プログラムは約 1.6〜1.8MB となる（ESP32 コア 2.0.17 の Core2 で約 1.59MB、3.3.12 の Core2 で約 1.76MB、CoreS3 で約 1.72MB）。Core2 の既定（6.5MB APP）と CoreS3 の既定（16M Flash：3MB APP）に収まる。1.2MB APP のパーティション（Default 4MB 等）では入らないので、そのときは「16M Flash (3MB APP/9.9MB FATFS)」か「Huge APP」を選ぶ。

### 6.9 キャリッジ制御（KnitCtrl_M5.ino / M5Stack Core2・CoreS3）

KnitCtrl_M5.ino は、シルバーリード電子キャリッジの DIN コネクタの信号（ONP・OCD・ON1・OPC）を M5Stack Core2 または CoreS3 の入力 INP・ICD・IN1・IPC で読み、選針を ONS からキャリッジの INS へ出す。INP のカウントはキャリッジが走り始めた位置で始まりが変わるので、針位置はすべてカーソル（パターンの目1 の基準針）を 0 とした相対値で扱う。最初に空通し（往復）でポイントカムとカーソルの位置を求め、往復で一致してから編み込みに入る。制御の本体は割り込みで動く ce::Engine（スケッチ内の CARRIAGE ENGINE の区間）で、Arduino の API に依存しないためホストで単体テストできる（9.2）。

| ON1      | ND1      | 6      | 赤             | 1       | カーソル。ネガティブインパルス |
| OCD      | HOK      | 7      | 灰             | 2       | キャリッジ方向。H = 左←右、L = 左→右 |
| INS      | DOB      | 8      | オレンジ       | 3       | 選針。H = 平編み、L = 編み込み |

M5キャリコンの GPIO は、M5 から見た向きで I と O を付け替えた記号で呼ぶ（rev.44）: ICD（キャリッジの OCD）、INP（ONP）、IPC（OPC）、IN1（ON1）、ONS（INS）。I は M5 へ入る信号、O は M5 から出る信号。キャリッジシミュレータ（SRCarriageSim）はキャリッジの代わりなので、キャリッジと同じ OCD・ONP・OPC・ON1・INS を使う。本書の M5キャリコンの説明（6.3.6・6.9 など）は M5 の記号で書く。

ONS の論理はキャリッジの INS と同じ L（GND）= 選針、H（5V）= 平編み（ONS_ACTIVE_HIGH = false。rev.46 で訂正。rev.45 までは H = 選針で出していた）。setupCarriageIo() は ONS を出力にする前に onsOff() で H を出力レジスタに入れ、出力にした瞬間に L（選針）を出さない。電源を入れてから setup() までは M5 が ONS を駆動しないので、インタフェース側で H（平編み）にプルアップしておく。

機種は M5.getBoard() で判定し、Core2 は PINS_CORE2、CoreS3（CoreS3 Lite を含む）と CoreS3 SE は PINS_CORES3 を使う。M5-Bus のピン番号は機種によらず同じで、GPIO 番号だけが違う（M5-Bus の番号は左列が奇数・右列が偶数。括弧内は配線メモの表記で、同じ段の左右を L／R と呼ぶ）。それ以外の機種（Basic・Fire 等）は表示専用で動く。Core2 の G36 は入力専用でプルアップがないのでインタフェース側で H に保つ。ESP32 の G36 は WiFi 動作中に短いグリッチで割り込みが入ることがあるため、IN1 の割り込みでは読み直して L のときだけ印を付ける（CoreS3 の G8 は内部プルアップを使う）。CoreS3 の G17／G18 はポート C（UART）、G8 はポート B と同じピンなので、それらのポートには何もつながない。選針出力は起動の最初に平編み（H）にする。

電源: M5 本体は M-Bus の 5V（28 番）からインタフェース基板と共有で受ける（MBUS_5V_INPUT = true）。setup() で M5.begin の前に cfg.output_power = false とし、本体から M-Bus へ 5V を出す回路を切る（M5Unified が setExtOutput(false) を呼ぶ）。Core2（AXP192）は GPIO0 を浮かせて昇圧を止め EXTEN を切り、Core2 v1.1（AXP2101）は BLDO2 を 0 にする。CoreS3（Lite・SE を含む）は AW9523 の BUS_OUT_EN と昇圧（BOOST_EN）を切り、M-Bus の 5V を入力側に切り替える。本体が 5V を出したまま外から 5V を入れると、本体の昇圧回路と基板の電源がぶつかる。書き込みなどで USB をつなぐときは、基板の 5V と USB の 5V が同時に入らないよう、基板側の 5V を切るか 5V を通さない USB ケーブルを使う（Core2 v1.1 は出力を切ると USB の 5V と M-Bus の 5V が本体内のスイッチでつながる）。基板の 5V 電源は M5 本体の消費（WiFi・LCD・音声）も見込んだ容量にする。基板を本体から給電する構成に戻すときは MBUS_5V_INPUT を false にする。

#### 6.9.2 信号の読み取りとトラバース

INP の立ち上がり割り込み isrInp で ICD・IPC・IN1 のレベルを読み、ce::Engine::step を呼んで、その場で選針を ONS へ出す。IN1 は立ち下がり割り込み isrIn1 で印を付け、INP の時点で L だった場合も拾う。1 つの L パルスは 1 回だけ数える。isrIn1 は、直前の INP の時点ですでに L だったパルス（isrInp がレベルで数えたもの）には印を付けない（rev.34）。割り込みから呼ぶ処理はすべて IRAM に置き、switch 文（ジャンプ表がフラッシュに置かれる）を使わない。loop とは portMUX の排他区間で値を受け渡し、割り込み側の出来事（空通しの往路・復路の始まり、判定、選針区間の出入り、編み終わり等）はイベントの輪バッファで loop へ渡す。

rev.33 までは isrIn1 が無条件に印を付けていたため、Core2 では同じパルスを二度数えることがあった。ESP32 の GPIO 割り込み（gpio_intr_service）は、端が同じ回にまとまると GPIO0〜31 を番号の小さい順に呼んでから GPIO32〜39 を呼ぶ。Core2 は INP = G13、IN1 = G36 なので、IN1 が INP↑ の割り込みの遅れ（数 µs）より短い間を空けて変わると、isrInp が先に IN1 = L を見てカーソルを数え、そのあと isrIn1 が印を立て、次の INP でもう一度数える。カーソル 1 つが「0, +1 目」の 2 つになり、空通しが往復とも「カーソルが2つ以上あります」で一致しない。キャリッジシミュレータ（SRCarriageSim）は ON1 を変えた直後（digitalWrite 1 回ぶん、約 1 µs 後）に ONP↑ を出すので、M5 では IN1 の直後に INP↑ が来て毎回起きた。実機でも ON1 と ONP がほぼ同時に変われば同じことが起きる。CoreS3 は IN1 = G8、INP = G18 で isrIn1 が先に呼ばれるので起きない。直したあとは、IN1 が INP↑ と同時でも、前後に数 µs〜1 ms ずれても、INP と INP の間だけの短いパルスでも 1 回だけ数える（9.2）。

トラバース = ICD が変わるまでの 1 方向の移動。ICD が切り替わってから IN1_GUARD（3 目）未満の IN1 はスタート・反転パルス、IPC↑ は編み出しパルス（またはカム区間の中から走り始めた）として扱い、カーソル・ポイントカムに数えない。IPC の H が MIN_SEG（2 目）未満で終わったものはノイズとして捨てる。ICD は走り始めてから数目遅れて切り替わる（ICD の遅れ）が、位置は区間の手前で合わせ直すので影響しない。INP が 0.4 秒（MOVE_IDLE_MS）来なければ止まっているとみなす。

#### 6.9.3 空通し（往復）とポイントカム・カーソルの照合

CALIB または本体の A ボタンで始める。開始側が右端なら往路は左へ、復路は右へ（左端なら逆）。指示した向きに動き出したときから往路を記録し、ICD が反転したら復路に移る。復路は、もう一度反転したとき、または止まったまま 1.5 秒（CAL_END_IDLE_MS）で終わりとし、判定する。往路・復路それぞれで、IPC の変化（↑・↓）とカーソル（IN1）を INP のカウントで記録する。IPC の変化 1 つがポイントカム 1 個に当たる（ポイントカムの針は区間に含まれる：↑の針が最初の H、↓の 1 つ前の針が最後の H）。

IPC を判定する位置（選針位置）と IN1 を判定する位置の差を「先行」と呼ぶ。片道だけでは先行とポイントカムの位置を分けられないので、同じポイントカムを往路と復路の両側から通ったカウントから求める。往路で i 番目に出会ったポイントカムは、復路では n−1−i 番目に出会う。

```text
t = （↑ ならそのカウント、↓ ならそのカウント − 1）− カーソルのカウント
2 × 先行 = −( t往[i] + t復[n−1−i] ) （i = 0..n−1。ばらつき ±1 目まで）
先行 off = 2 × 先行 の平均を丸めた値 （|off| ≦ 80）
PC(i+1) の針位置 q = 往路の向き × ( t往[i] + off ) （カーソル = 0、右が +、向き: 左へ −1 / 右へ +1）
選針区間 = [PC1, PC2]、[PC3, PC4] （PC は往路で出会った順。3 個なら PC3 は無視）
```

| **照合**         | **条件**                                                                   | **理由**       |
|------------------|----------------------------------------------------------------------------|----------------|
| カーソル         | 往路・復路とも IN1 がちょうど 1 回（スタート・反転パルスを除く）           | 1 なし／2 複数 |
| ポイントカムの数 | 往路と復路で IPC の変化の数が同じ                                          | 8              |
| 選針区間         | ポイントカムが 2 個以上（PC1・PC2）。PC1・PC2 がなければパターンを出せない | 4              |
| 上限             | ポイントカムは 4 個まで                                                    | 16             |
| 先行             | すべてのポイントカムで ±1 目以内に一致し、\|off\| ≦ 80                     | 32             |
| 向き             | 空通し待ちで、指示と逆向きへ 8 目（WRONG_DIR_N）動いた                     | 64             |
| 記録             | 1 パスで IPC の変化 12 個・カーソル 4 個まで                               | 128            |

PC3 だけで PC4 がない（往路で IPC が上がったまま下がらない）ときは、ポイントカムが 3 個として往復が一致すれば PC3 を無視し、PC1–PC2 だけを選針区間にする（STATUS \[11\] bit0、音声 20）。このとき IPC は往路と復路で別の区間を示すので、選針区間の中かどうかは IPC ではなく位置だけで判定する（6.9.4）。

一致すれば段階 4（空通し完了）にし、音声 05 で送信開始を促す。キャリッジは開始側にあり、次に動かす向きは往路と同じ向きになる。一致しなければ空通し待ちに戻し、理由（音声 08／09／21）と音声 06、置き場所の案内（01／02）を続けて鳴らす。空通しの結果（先行・ポイントカムの位置・区間・各向きの基準テンプレート）は電源を切ると消える。ポイントカムやカーソルを動かしたら空通しをやり直す。

往路・復路それぞれで検知したカーソル（IN1_GUARD 以降の IN1）は、INP のカウントで 4 つまで記録し、STATUS \[27..39\] で、その向きで最初に検知したカーソルを 0 とした進行方向の目数として知らせる（6.3.6）。アプリはキャリッジ欄に「カーソル検知 往路← 0, +1目 ／ 復路→ 0, +1目」のように出す（5.5）。判定のときはシリアルにも「\[CAL\] cursors out: 0 +1 back: 0 +1」のように出す。照合の条件（往復とも IN1 がちょうど 1 回）は変えていない。

#### 6.9.4 編み込み（選針と ACK）

空通しが済んだあと、最初の ROW_DATA で編み込みを始め（段階 5）、音声 10／11 で動かす向きを案内する。ROW_DATA のパスは次のトラバース用に置き（縦2倍は 2 回ぶん）、ACK はまだ返さない。STOP、MODE_ENTER（スタートし直し）、送信相手の切断で編み込みを止め、置いたパスを捨てて選針を OFF にする。

各トラバースでは、IPC の変化を同じ向きの空通しで記録した変化（基準テンプレート）に合わせてカウント j（カーソル = 0）を決める。位置が分かっていれば予測に一番近い同種の変化、分かっていなければ順番どおりの変化に合わせる。カーソルを通ったら j = 0 とする。選針位置の針は q = 向き × (j + 先行) で、q が選針区間に入ったときに置いてあるパスをそのトラバースに割り当てる。区間の中では、IPC が H のとき（PC3 を無視したときは IPC によらず）パターンの目 m = q mod マーク数（目番号はカーソルから右へ増える。横2倍は m ÷ 2 の目）のビットを出す。マークの外側へも左右に繰り返す。

| **出来事**                | **条件**                                                    | **動作**                                                                        |
|---------------------------|-------------------------------------------------------------|---------------------------------------------------------------------------------|
| 区間に入る（BIND）        | 選針区間に入った。パスが置いてある                          | そのパスで選針する。制御 bit3（ブザー）なら鳴らす                               |
| データなし（NODATA）      | 選針区間に入ったが、パスが置いてない                        | そのトラバースは平編み。音声 13、警告 1。パスはそのまま次のトラバースで使う     |
| 編み終わり（DONE）        | 最後の選針区間を抜けた（全区間を通った）                    | ACK を返す。縦2倍は 1 回目で同じパスを置き直し、2 回目で ACK                    |
| 途中の折り返し（PARTIAL） | 区間を抜ける前に折り返した／区間の途中から始めた            | 同じパスをもう一度編む。折り返した直後のトラバースは選針しない。音声 14、警告 2 |
| 位置ずれ（SYNC）          | IPC の変化・カーソルが予測と 2 目（SYNC_TOL）を超えてずれた | 音声 15（空通しのやり直しを案内）、警告 4。位置は数え続ける                     |

SRパタコン（送信相手のクライアント）が BYE を送って切断したとき（rev.35。rev.37 で BYE のあとの切断と A+C の切断に限った）: 送信中なら編み込みを止め（音声 12）、空通し完了・未較正なら接続待ちの画面にする（従来どおり）。空通し待ち（段階 1）なら空通しはそのまま待たせて画面を接続待ちにし、まだ鳴らしていない置き場所の案内を捨てる。不一致で空通し待ちに戻ったあとの切断も同じ。つなぎ直すと（MODE_ENTER・CALIB・ROW_DATA・STOP を受けると）空通し待ちの案内に戻り、音声 19 に続けて置き場所の案内（01／02）を鳴らす。接続待ちの画面のままキャリッジを動かしても空通しは記録され、往路の案内に変わる。往路・復路の途中で切れたときは案内をそのまま出して空通しを続け、終わったら完了・不一致とも接続待ちの画面にする（結果はつなぎ直したときの STATUS で SRパタコンへ届く）。本体の A・B ボタンで空通しを始めたときは、アプリにつながっていなくても置き場所の案内を出す（g_appLost を消す）。探索のプローブの切断では画面を変えない。

rev.37 では、接続待ちの画面にするのを、起動直後と、SRパタコンの「切断」（BYE のあとの切断）・本体の A+C 長押しで切ったときだけにした。BYE なしで切れたとき（ネットワーク等。WebSocket のハートビート（7.4）で見つけた切断を含む）は画面を変えず、その段階の案内をそのまま出す（g_linkDrop）。再接続を促す表示は出さない。送信中だったときは、送る相手がいないので従来どおり編み込みを止め（音声 12）、空通し完了の案内にする。SRパタコンがつなぎ直せば（MODE_ENTER・CALIB・ROW_DATA・STOP を受ければ）そのまま続く。本体の A・C ボタンを同時に KICK_HOLD_MS（2000 ms）押すと、つながっているクライアントすべてへ切断要求（0x85）を送り、短く鳴らして、すぐ接続待ちの画面にする（kickApp）。送信中なら編み込みを止める。SRパタコンは BYE を返して閉じる。KICK_WAIT_MS（1000 ms）たっても閉じない相手は M5キャリコンから切る。未較正の案内の最下行のボタンの割当に「A+C(hold):BYE」を加えた。 rev.42 では、送信相手の生存確認を 10 分にした（7.4）。応答が 10 分途絶えて M5キャリコンが切ったときは音声 24 で警告し（送信中なら編み込みを止めて続けて音声 12）、相手が BYE なしで閉じたときは、送信中なら従来どおりすぐ編み込みを止め（音声 12）、そこから LINK_TIMEOUT_MS（10 分）つなぎ直さなければ音声 24 で警告する（g_lostWait。つなぎ直す・BYE・A+C で取り消す）。SRパタコンの「切断」（BYE のあとの切断）と A+C で接続待ちの画面になったときは音声 23 を鳴らす（送信中だったときは音声 12 のあと。A+C は送信相手がいたとき、または接続待ちでなかったときだけ）。往路・復路の途中で切れて接続待ちにならないときは鳴らさない。

#### 6.9.8 実機で確かめていない前提

次はロジックアナライザーの解析結果と波形からの推定で、実機での確認を待つ（10.）。選針（ONS）を INP↑ の直後に出してよいこと、ポイントカムの針が区間に含まれること、目番号がカーソルから右へ増えること、IPC と IN1 の判定位置の差を「先行」1 つで表せること、スタート・反転・編み出しのパルスが ICD の切り替えと同時に出ること、PC3 だけのときの IPC の出方。合わないときは 6.9.7 の定数で合わせる。

## 7. 機器探索と接続管理

### 7.1 探索プロトコル

探索は指定サブネットの /24 全域（.1 から .254）に対して短時間の WebSocket 接続を試み、識別要求に応答した機器を収集する方式である。

```text
クライアント → 機器 : [0x10]
機器 → クライアント : [0x90][接続元IP 4byte][ホスト名 …]
```

応答に含まれる「接続元IP」は、機器から見たクライアントのIPアドレスである。これを利用してサブネットを自動判定できる。WebRTC を用いた従来のローカルIP検出手法よりも確実であり、ブラウザのプライバシー制限の影響も受けない。

### 7.2 探索の制御

走査の状態は、表示用の scanning と判定用の scanOn の2つで持つ。ボタンの表示が「検索」に戻っているときは、scanOn が真のままでも停止指示とみなさず必ず新しい走査を始める。また状態の後始末は finally に置く。これにより、途中で例外が出ても「押しても何も起きないボタン」にならない。

### 7.3 プローブソケットの管理

探索中に開いた WebSocket は probeSockets（useRef が保持する Set）に登録され、完了時に取り除かれる。接続を試みる直前には必ず killProbes() を呼び、在庫のプローブソケットをすべて明示的に閉じる。

```js
const killProbes = () => {
probeSockets.current.forEach((w) => { try { w.close(); } catch (_) {} });
probeSockets.current.clear();
};
```

この処理は必須である。M5Stack の WebSocket サーバは同時接続スロット数が限られており、探索で開いた接続を残したまま本接続を試みるとスロットが枯渇して接続に失敗する。またコンポーネントのアンマウント時にも、タイマーとあわせてすべてのプローブソケットを閉じる。走査の開始時にも killProbes() を呼ぶ。前回の探索で閉じ残しがあると機器側のスロットが埋まったままになり、2回目以降の検索で1台も返らなくなるためである。

### 7.4 接続確立と自動再試行

doConnect() は接続の確立可否を opened フラグで追跡する。接続が確立する前に close イベントが発生した場合、500ms 後に一度だけ自動再試行する。これは探索直後に機器側がスロットを解放しきるまでの猶予を与えるためであり、再試行は1回限りとして無限ループを防いでいる。

```js
ws.onclose = () => {
const wasOpen = opened;
if (wsRef.current === ws) wsRef.current = null;
setConnected(false); setSelected(null); setReady(false);
if (!wasOpen && retry) { // 確立前に閉じられた
setWsState("再接続中…");
later(() => doConnect(url, key, false), 500); // 1回だけ再試行
} else {
setWsState(wasOpen ? "切断" : "未接続");
}
};
```

なお機器側ファームウェアは、応答のない古いクライアントスロットを回収する。M5Stack の WebSocket サーバはスロットを自動解放しないため、回収しないと繰り返し探索を行った場合に接続不能となる。rev.41 までは webSocket.begin() の直後に webSocket.enableHeartbeat(15000, 3000, 2) を設定して全クライアントに同じハートビートを使っていたが、rev.42 では使わず、loop の wsHeartbeat が WS_PING_INTERVAL_MS（15000 ms）ごとに全クライアントへ ping を送り、最後に応答（pong・BIN・TEXT・ping）があった時刻から、送信相手（g_mainClient）は LINK_TIMEOUT_MS（600000 ms = 10 分）、それ以外は PROBE_TIMEOUT_MS（36000 ms）で webSocket.disconnect(num) する。ブラウザは ping に自動で pong を返すので、タブを裏にしても応答は続き、タブレットがスリープすると途絶える。

確立済みの接続が閉じたときは、自動ではつなぎ直さない（rev.36 で入れた 10 回の再接続は rev.37 で取りやめた）。確立前の 1 回だけの再試行は上のとおり。M5キャリコンは、応答のなくなった送信相手（スリープしたタブレットのブラウザ等）を 10 分待ってから切る（rev.42。それまではハートビートで約 33〜48 秒）。BYE のない切断なので M5キャリコンの画面は変えず、音声 24 で警告する（6.9.5）。スリープから 10 分以内に戻り、OS が接続を保っていれば、そのまま転送を続けられる。

### 7.5 接続状態と画面遷移

| **状態表示**                 | **条件**                                 |
|------------------------------|------------------------------------------|
| 未接続                       | 初期状態、または接続確立前に切断された   |
| 接続中…                      | WebSocket の接続処理中                   |
| 再接続中…                    | 確立前の切断を検出し、自動再試行を待機中 |
| 接続済み                     | open イベント受信済み                    |
| 切断                         | 確立済みの接続が閉じられた               |
| エラー（模擬サーバで検証可） | 接続に失敗した                           |

接続が成立すると 検索段は非表示となり、ヘッダー段に接続先と切断ボタンが現れる。切断すると検索段が再表示される。これにより、接続後は転送操作に必要な要素のみが画面に残る。

### 7.6 接続先の記憶と自動再接続

編み機コントロールは knitCtrl による条件付き描画なので、閉じると KnitControl はアンマウントされ、接続状態も含めて内部状態をすべて失う。そこで接続先の記憶は親（KnitPatternMaker）の lastConn に置く。接続が確立した時点で onConnInfo により { url, key, subnet, port } を親へ預け、次に開いたときはこれを各入力の初期値にしたうえで、開いた直後に一度だけ自動で接続し直す（状態表示は「再接続中…」）。自動再接続を試みるときは、サブネット自動取得のためのシード問い合わせは行わない（同じ機器へ余分なソケットを開かないため）。つながらなければ doConnect が 500ms 後に一度だけ再試行し、それでも駄目なら通常の検索段に戻る。検索段には「前回つないだ … へ自動接続しています」と出し、手動での検索・接続に切り替えられることを示す。切断ボタンで切っても記憶は消さないので、開き直すとまた同じ機器へつなぎ直す。別の機器へつなぐときは検索または手動URLで選び直す。

アンマウント時には、プローブソケットとタイマーに加えて本接続も必ず閉じる。閉じ残すとブラウザはページが生きているあいだソケットを保つため、機器のクライアントスロットを占有し続ける。arduinoWebSockets のサーバはスロット数が限られており（既定5）、コントロールの開閉をくり返すと空きが無くなって、探索で1台も応答しなくなる。閉じる前に onopen / onclose / onerror / onmessage を外し、アンマウント後の状態更新と自動再試行（onclose 経由）が走らないようにする。閉じる前に BYE を送り、M5キャリコンに利用者の切断であることを知らせる（rev.36。ページを離れるときも pagehide で BYE を送ってから閉じる）。実測では、修正前は開閉3回で3本が残り、修正後は毎回0本に戻る。

## 8. 画面描画

### 8.1 二段構えのCanvas描画

編み機コントロールのパターン表示は、描画コストを抑えるため2枚の Canvas に分離している。

- オフスクリーンCanvas（patC）— パターン本体とグリッド線を描画する。パターン内容・目数・段数が変化したときのみ再描画する

- オンスクリーンCanvas（viewRef）— オフスクリーンの内容を転写したうえで、段の状態を半透明で着色する。カーソル移動のたびに再描画するが、コストは転写1回と矩形数個ぶんに留まる

セルサイズは6ピクセル固定であり、CSS の image-rendering: pixelated により拡大時のぼけを防いでいる。

編み機コントロールのパターン表示は、編集・表示モードと同一の向きで描画する。段1が最下段、段Rが最上段であり、内部段インデックス i がそのまま表示行となる。パターン本体・状態着色・開始段ハイライトのいずれにも向きの変換を行わない。以前の版では制御モードのみ上下を反転し、段1を最上段へ配置していたが、編集画面と見比べたときに図案が反転して見えるため取りやめた。

パターン本体の配色は編集・表示モードと対応させる。選針された目はそのパスの色（最終パスは地色）で塗る。非選針の目の扱いは色数で分ける。2色（1パス）は非選針がそのまま地色で編まれるため、地色（色0）をそのまま敷き、表示モードと同じ見え方にする。3色以上は、各パスの非選針が「このパスでは編まない」という意味でしかなく、実際に地色で編まれるのは最終パス（地色の柄）で選針された目である。そこで非選針には地色を大きく暗くした色（shade −0.86）を敷き、最終パスの地色そのものと見分けられるようにする。

5目・5段ごとの目安線は、暗い地の上では白（不透明度0.06）で引く。2色で明るい地色（輝度0.55超）を敷いたときは線が見えなくなるため、黒（不透明度0.10）へ切り替える。

### 8.3 変換プレビューアイコン

各変換ボタンには、22×24 ピクセルのアヒル図案（DUCK）へ当該変換を適用した結果をアイコンとして表示する。ボタンの背景色ではなく図柄そのものが変化するため、どの変換が有効かを直感的に把握できる。ミラーとシェブロンについては、連結後の目数が異なることを示すため専用の図案を用意している。

転送中（running）はすべての変換ボタンを無効化する。転送途中で変換が変わるとパターン寸法が変化し、機器側の状態と齟齬を生じるためである。変換を変更した場合は resetTx() により転送状態を初期化し、MODE_ENTER から再通知する。

### 9.3 4ファイル同期の原則

あらゆるコード変更は、.tsx / .jsx / CDN版 .html / オフライン版 .html の4形式すべてへ同時に反映しなければならない。1形式のみを更新すると、以後どの形式が正本か判別できなくなる。オフライン版は外部依存を持たず実機環境で確実に動作するため、実際の検証対象としては最も重要である。取り違えを防ぐため、画面のヘッダー（主画面・編み機コントロール・検索段の見出し）に版表記 APP_REV を出す。主画面ではアプリ名「SRパタコン」を白地に黒で出し、その脇に版を黒地に白のチップで出す。編み機コントロールでも見出しの脇に同じ黒地に白のチップで出し、ツールチップに版の日付 APP_DATE と対応するファイル形式の版（4.4.8）を示す。ブラウザのタブ名も「SRパタコン rev.xx」とする（起動時に document.title を設定し、HTML の \<title\> もビルド時に同じ文字列にする）。機能を変えたときは APP_REV と APP_DATE を更新し、4形式を生成し直す。画面の版表記が手元の版と違っていれば、古いファイルを開いているか、生成し直していないということである。

## 付録B. 制御4bitのビット割当

### B.1 アプリ内部表現

アプリ内部の制御4bit（doc.control の各要素、WSプロトコルの ROW_DATA \[4\]）は次の割当である。この順は WebSocket プロトコル・機器ファームウェア・画面描画・編集操作で統一されており、変更しない。

| **ビット** | **値** | **意味**                         |
|------------|--------|----------------------------------|
| bit3       | 0x08   | ブザー（最終バイトの bit7 相当） |
| bit2       | 0x04   | 指示記号ビット a                 |
| bit1       | 0x02   | 指示記号ビット b                 |
| bit0       | 0x01   | 指示記号ビット c                 |

ブザー（bit3）は指示記号とは独立に立てられるため、記号表示とブザー鳴動を組み合わせて指定できる。

### B.2 指示記号の対応（内部表現の下位3bit）

| **下位3bit** | **記号** | **備考** |
|--------------|----------|----------|
| 1            | \>       | 指示記号 |
| 2            | ＊       | 指示記号 |
| 3            | }        | 指示記号 |
| 4            | \<       | 指示記号 |
| 6            | {        | 指示記号 |
| 0, 5, 7      | （なし） | 記号なし |

表示に用いる文字は \< \> { } および ＊ である。以前の版では矢印文字（←・→・⇦・⇨）を用いていたが、小さなセル内で向きが判別しにくく、環境によって字形も揺れるため改めた。実装は CTRL_SYM の対応表1か所で定義しており、下位3ビットが 0・5・7 のときは記号を表示しない。制御4ビットの値そのものと機器側のビット割当は変更していない。

### B.3 U-BOX／PC10 バイナリでのビット割当（内部表現の逆順）

U-BOX メモリカードと PC10 .DAT のバイナリは、制御ニブルのビット順がアプリ内部表現と逆であり、かつ両形式で同一である（いずれも実機確認済み）。機器側の割当は次のとおり。

| **機器ビット** | **意味**       | **内部表現での対応ビット** |
|----------------|----------------|----------------------------|
| bit0           | ブザー         | bit3                       |
| bit1           | 下送り（段 +） | bit2                       |
| bit2           | 上送り（段 −） | bit1                       |
| bit3           | （予約）       | bit0                       |

このため parseUBox（読み込み）と buildPC10（書き込み）では、最終バイト上位ニブルに対して nib4rev によるビット反転を施し、内部表現との間で相互変換する。内部表現側および WebSocket プロトコル側のビット順は変更しない。この反転は実機との往復（U-BOX 読込 → PC10 書出し）で保存されることを単体テストで確認済みである。
